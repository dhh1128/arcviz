M-Wong
Oct 14, 2024

One thing that I feel is missing from the OCA specification in regards with the Aries Branding Overlay and the Cluster Ordering Overlay is attribute aggregation.
The branding example defines the following primary and secondary attributes:

{
    "primary_attribute":"firstname",
    "secondary_attribute":"lastname"
}

In the Aries OCA style guide these two attributes are displayed as two separate text fields in the card layout.
Oftentimes it would make sense to display the full name as one text field, but right now that would require the issuer to include an additional attribute fullname in its credential and the capture base, so it can be used in a presentation overlay.
Maybe there could be an additional transformation overlay that allows attribute aggregation? Something like this:

{
    "type": "spec/overlays/template/1.0",
    "capture_base": "...",
    "attributeTemplates": {
        "fullname": "{{ firstname }} {{ lastname }}"
    }
}

In the OCA processing code, the fullname attribute value would be resolved by treating values inside the brackets as references to other regular attributes.
Then, fullname could be used as the brandings primary_attribute, while the Cluster Ordering Overlay could still use firstname and lastname separately in its clusters.

One issue I see with this kind of overlay, is that it either requires some overlays (e.g. the label or information overlays) to be aware of the new properties produced by this overlay, or that the capture base needs to include the aggregated attribute as well (which could potentially lead to conflicts if the capture base doesn't use the attribute type TEXT).

Is this a topic that was already discussed or needs to be considered for the specification (either the official OCA or the Swiss OCA one)?

bj-ms Oct 14, 2024
Author

Attribute aggregation is definitely a discussion that we have had and it comes down to the issue of creating dependencies between overlays.

I would argue that we would have to extend the definition of the Capture Base from the OCA specification rather than create an additional overlay because of the dependency issue. There is currently no way to define an overlay dependency or priority, and I would say that this is not the intent of the OCA specification.

Additionally, this could raise the question of what to include in the Capture Base. For example, how should we handle JSON pointers? Should they be in the capture base as part of the attribute name as currently defined in the specification, in a separate object in the capture overlay, or completely separate as an overlay?

And on the topic of Aries Branding Overlay, we mention in the Swiss OCA specification that it is up to the implementers to interpret the Aries Branding Overlay values.
This means that an Issuer won't be able to force a wallet implementer to have the primary and secondary attributes displayed on one or multiple lines.

We will take notes and this is definitely a topic to follow up on.

bj-ms Oct 15, 2024
Author

I think this is a good opportunity to clear up some misunderstandings.

The fundamental problem we want to solve is to find a generic solution for how to visualize verifiable credentials in the wallet (relying parties do not need the OCA bundle).
This means not only how a credential should look like, but also how the data should be interpreted.
A good example is when you are given a string. When you parse that string, we will not always know what it represents. It can be very useful to know that it is a data URL and that it represents an image.

OCA has some ideas that we think are relevant:

  • Defining a finite set of attributes
  • Applying specialized overlays to the set of finite attributes
  • Integrity between filename and content of the OCA bundle
  • Multilanguage support

In addition, there are efforts by the Aries project to use OCA to visualize Verifiable Credential, which we found to be a relevant option.
It made sense to base our specification on an existing technical specification and try to avoid creating just another specification.
We created the Swiss OCA specification because we felt the need to clarify points that were not clear enough in the OCA specification and to add or remove features that we felt were relevant.
We are also discussing with the peo in the Aries project if we can find a way to get to a single technical specification.

Also, the Human Colossus Foundation behind the OCA specification is aware of our work and we are trying to get as much feedback as possible for this use case.

To accomplish this task, I will try to summarize your feedback in the following bullet points:

  • CESR and SAID are not recognized standards and would like to see them replaced by a standardized format.
  • You feel that not all parts of OCA are necessary and suggest that we try to strip the specification down to the bare minimum and reconsider whether we still need OCA.

Can you please validate that I understood your feedback correctly?

mitfik
Oct 16, 2024

Dear all,

I'd like to clarify a few points about the Overlays Capture Architecture (OCA) and its current development at HCF to help you better leverage it for your projects.

OCA - Overlays Capture Architecture was designed to capture and understand the context and meaning of information for further processing and portability, particularly in terms of interoperability and data flows. This means that when you receive a data package, OCA enables you to comprehend the context in which this information was captured and its intended meaning.

To ensure functionality across different jurisdictions, a critical aspect of OCA is its integrity. Everything within OCA is content-addressable through SAIDs (Self-Addressing Identifiers), ensuring the integrity of data irrespective of its source. This is crucial for maintaining cross-governance compatibility.

For comparison, consider the schema.org/person model. When you use this schema, you cannot be certain that the content it references matches your expectations. This ambiguity opens up potential attack vectors, particularly in the Verifiable Credentials (VC) space. For example, by altering the meaning of a schema, you could change the outcome of a validation process, such as the difference between "Are you allowed to enter?" versus "Are you NOT allowed to enter?" if a simple affirmative 'yes' is misinterpreted or maliciously modified.

Important to mention as well is that VC use case for OCA is relatively small and one among of many use cases where OCA shows it strength in space of data capture/collection and processing.

P.S. OCA follows dominant design - we build, we test and then if it works becomes de facto standard. Writing a spec or "standard" does not mean that is good or that everyone should use it. At HCF we have more practical approach.

pknowl
Oct 16, 2024

Allow me to introduce myself: I am @pknowl, the inventor of the Overlays Capture Architecture (OCA) concept and the founder of the overarching framework, Decentralised Semantics. I currently chair the Decentralised Semantics Working Group at The Human Colossus Foundation. My leadership primarily focuses on ensuring semantic interoperability and data harmonisation through utilising OCA, defending its core principles, while @mitfik focuses on the ecosystem of tools required to maintain the integrity of OCA as a decentralised semantic architecture.

Regarding @M-Wong 's query on attribute concatenation and the structural treatment of a citizen's name in semantic modelling, I'd like to provide a perspective that balances semantic precision and data protection. Rather than introducing a transformation overlay that aggregates attributes (such as firstname and lastname into fullname), the best practice is to treat "Name" as a referenced OCA bundle from the parent schema. This allows for a more detailed and accurate representation of the structural components of an individual's name while maintaining flexibility in how to present that information.

Here is an example of how a "Name" object can be structured as a referenced capture base:

{
  "type": "spec/capture_base/1.0",
  "classification": "NOGA:8411",
  "digest":"xxxxxx",
  "attributes": {
    "firstName": "Text",
    "middleName": "Text",
    "lastName": "Text",
    "fullName": "Text",
    "alias": "Text",
    "honorificPrefix": "Text",
    "honorificSuffix": "Text",
    "preferredName": "Text",
    "nickname": "Text",
    "maidenName": "Text"
  },
  "flagged_attributes": [
    "lastName",
    "fullName",
    "alias",
    "maidenName"
  ]
}

Why this approach matters:

By treating "Name" as a granular and well-defined standalone object, we gain significant advantages from a PII (Personally Identifiable Information) protection perspective. This allows us to:

  1. Ensure granular PII flagging: Attributes such as lastName, fullName, alias, and maidenName are clearly flagged as PII due to their potential to uniquely identify an individual. Meanwhile, firstName may remain unflagged unless combined with other attributes (like lastName), ensuring accuracy in data classification.

  2. Support for internationalisation and flexibility: You've correctly pointed out that different cultures handle names differently. By breaking the name down into distinct elements (e.g., firstName, lastName, alias), we allow for flexibility in how names are captured and displayed across different regions and contexts without enforcing a rigid, one-size-fits-all structure.

  3. Early introduction of PII protections upstream: By defining and flagging these sensitive attributes at the structural level, we ensure that PII considerations are embedded early in the data lifecycle. This prevents potential exposure of sensitive information downstream, especially in contexts where data is shared across systems or jurisdictions.

  4. Alignment with semantic interoperability: Defining the structure of "Name" in this manner supports broader semantic interoperability and data harmonisation efforts. This allows for seamless data exchange across different systems and jurisdictions, ensuring consistency while respecting local privacy regulations.

In summary, while a transformation overlay for concatenating attributes such as firstname and lastname may offer a temporary solution, the recommended approach within the OCA framework is to represent "Name" as a structured, granular schema of its own. This supports more accurate PII handling, maintains flexibility, and aligns with the long-term goal of semantic interoperability.

Please don't hesitate to reach out if you have further questions from a semantic modelling perspective or would like to explore this in more detail. I’ll keep an eye on the ongoing discussion and jump in if I feel I can contribute to any further discussion points.

Hello, I am Carly Huitema and I am leading the implementation of OCA into what we've called the Semantic Engine at Agri-food Data Canada (ADC). We like the overlay structure of OCA and the calculation of SAIDs for reproducibility, an important feature in research. We have a publication which also explains the approach.

We are also at the stage of creating new overlays to add to our schemas. However, our approach is a little different. We want to keep new overlays separate from the official specification, to preserve interoperability and keep things clear about what is created by us, and what is within the core OCA specification. Since SAIDs are calculated at the object level we want to avoid mixing OCA spec and our own overlays together in the same object where a SAID is calculated.

This draft specification is our design that we are currently implementing from. It is currently in my personal repository while being developed and if others are interested in developing it with us at ADC it could become a community effort. Right now we have objects: oca_bundle (core spec OCA), extensions (our overlays we add) and presentation (where we will stick presentation specific overlays). We can add other objects. We have code and can generate our own overlays and calculate SAIDs and generate the package.

The OCA Package is an attempt to add to OCA the functionalities we need while maintaining SAID values and providing guidance to harmonize syntax.
