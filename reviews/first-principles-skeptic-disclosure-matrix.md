## Executive summary

The motivating problem is real, present, and observed — shipped wallets collapse a nine-way verification question to one checkmark, and the project's own production vLEI capture is an artifact on which the whole-chain green check would be a lie today. This is not generality chasing a hypothetical, and the document has already exercised minimality discipline in the one place my lens cares most about: it deleted an axis the commissioning brief asked for and merged two others, on argument rather than taste. I do not recommend rejection and I have no CRITICAL finding.

What I do find is a default chosen in the optimistic direction by the one document whose entire thesis is that optimistic defaults are the bug. Rule 2b makes the four-valued verification outcome space the default and host-declared degradation the exception, when on the only reference substrate that exists the degraded space is the truth for every check the renderer did not itself compute. Below that: one confidence-tier claim is factually wrong in a way that inverts its own conclusion (H6's discriminator over-fires on ordinary keripy artifacts rather than having no artifact at all), one host interface is sized at seven named channels with zero providers, and one closed open-question rests on keripy behavior that upstream fixed.

## Steelman

Take the strongest reading first, because it survives most of my prior.

The null hypothesis here would be: "render the credential, show whatever status the substrate hands you, and skip the epistemics." That do-nothing position is already refuted by evidence in hand, not by anticipation. The real vLEI chain is missing the root `EDP1vHcw…` KEL entirely, so delegation-to-root is unperformable from the payload; it contains no `rev` events, which proves only that none were captured. A renderer built on the status quo shows that artifact as fully verified. That is a present failure on present production data, which is exactly the bar I hold proposals to and it clears it on the first page.

The second thing the document gets right by my lens is subtractive. The brief asked for a "Form" axis and it refused, on three grounded arguments: variants co-occur freely (`spec-body.md:1775`, "All the Graduated Disclosure mechanisms MAY be used in combination" — re-confirmed), a signature on any variant verifies the Issuer's commitment to any other (`:1822`, "This cross-variant Issuer commitment verifiability is an essential property" — re-confirmed), and two of the seven variants are not visibility degrees at all. It then folded the brief's separate "Form" and "Field epistemics" axes into one per-unit H axis on the grounds that the `d`+`u` mechanism is uniform at every level — which the spec bears out, the same UUID-blinding paragraph appearing verbatim for Attribute blocks (`:340`), Aggregate elements (`:700`), Edge-groups (`:1093`), Edges (`:1162`), Rule-groups (`:1275`) and Rule sections (`:1311`). Five axes where the brief wanted six or seven, argued down rather than filled in, is minimally-sufficient-means practiced rather than cited.

Third: R0 was added because a reviewer objected that store presence already implies verification, and the answer is a genuinely useful narrowing rather than a defense — store presence warrants checks 1, 2 and a transitively-constructed 6/7, and explicitly not revocation, because `processCredential` saves revoked credentials on purpose (re-confirmed on `upstream/main`, `src/keri/vdr/verifying.py:142-145`: "no escrow, credential has been revoked… so we save a revoked credential"). That is a demand-driven addition with a code-level warrant, not a cell added for symmetry.

So my report is not "does this need to exist." It exists. My findings are about size and defaults.

## Top findings

### F1: Rule 2 makes the optimistic outcome space the default, against the document's own principle

- **Severity:** HIGH  **Confidence:** CONFIRMED  **dedupe_key:** `verification-outcome-space-optimistic-default`  **Objective function:** survivability  **Layer:** acdc
- **Location:** proposal §B3 and §d Rule 2b ("The host interface must let a host declare a check's outcome space degraded to {pass, not-pass}"); re-anchored: `src/keri/core/serdering.py:621-628`; `src/keri/vdr/verifying.py:153-161`, `:186-191`, `:446-452`, `:461-479`; `src/keri/vdr/eventing.py:1144` — all on `upstream/main` `e2a1e35ca`.
- **Finding.** The four-valued outcome space {pass, fail, unperformed, unperformable} is made the default for all nine checks, and the collapse to {pass, not-pass} is an opt-in a host must *declare*. On the reference substrate the polarity is backwards. `fail` is not reachable for checks 1–4 through a keripy-fed host: a `SerderACDC` cannot be constructed at all from bytes whose SAID does not recompute (`serdering.py:621-628`, the `if verify: self._verify()` gate raising `ValidationError`), schema failure throws `FailedSchemaValidationError` before the credential is stored (`verifying.py:153-161`), and a signature or anchoring failure means the event never enters the KEL. For checks 6 and 7 the proposal already concedes {pass, not-pass}, and I re-confirmed the mechanism: `verifyChain` returns `None` for a genuine violation (`op == 'I2I' and issuer != farIssuee`, `verifying.py:478-479`) and for far-node absence alike (`:419-420`, `:471-476`), and `processCredential` routes both to one `MissingChainError` and one escrow (`:186-191`). For check 9 the result is an ephemeral cue, not a stored outcome. `Tever.vcState` (`eventing.py:1144`) is the lone re-queryable status.
- **Why it matters.** A host that supplies nothing gets the full four-outcome space by default, which means a renderer will present a "fail" indicator as *available and simply not asserted* on a check whose substrate can never assert it — the absent flag read as meaningful, which is the exact failure Rule 2's own test forbids ("An application MUST NOT render an absent flag as a positive assurance"). It also sizes everything downstream: Phase 2C owes fixtures for 36 cells and Phase 3/4 owes an API carrying a distinction that has no provider. The proposal's own pair 10 is this finding in miniature; it just did not generalize it into the default.
- **Recommendation.** Invert 2b. Make {pass, unperformed, unperformable} the default outcome space and `fail` the opt-in fourth outcome a host declares it can supply — which it honestly can when arcviz itself recomputes checks 1 and 2 over raw bytes, and cannot when it is fed from a store. Then checks 6 and 7 need no special-case degradation clause, and the R0 posture ("store-fed, nothing recomputed") becomes the conformance baseline rather than an exception. This is smaller than what is proposed and strictly more honest.

### F2: H6's confidence tier is wrong, and the correction inverts Rule 12

- **Severity:** MEDIUM  **Confidence:** CONFIRMED  **dedupe_key:** `metadata-acdc-empty-u-discriminator-overfires`  **Objective function:** survivability  **Layer:** acdc
- **Location:** proposal §e ("H6 — Metadata ACDC — no fixture anywhere exercises an empty top-level `u`") and §d Rule 12; re-anchored: `tests/acdc/test_messaging.py:2367, 2430, 2813, 2876, 3713, 4339`; `src/keri/acdc/messaging.py:150-151`; `spec/spec-body.md:168`; arcviz `corpus-vlei-chain.md:59`.
- **Finding.** The claim is false: six fixtures on `upstream/main` serialize an ACDC with an empty top-level `u`. `test_messaging.py:2367` is an `acg` ACDC with a fully populated `A` aggregate and `'u': ''`. Per the spec's own discriminator — "An empty, top-level UUID, `u`, field appearing in an ACDC indicates that the ACDC is a metadata ACDC" (`spec-body.md:168`, re-confirmed) — those artifacts *are* metadata ACDCs. They are plainly not metadata offers; `u` is simply the unset default in keripy's ACDC field maps, which list `u=''` in both `alls` and `opts` (`messaging.py:150-151`). Meanwhile the genuinely public credentials in the real vLEI capture *omit* `u` rather than emptying it (`corpus-vlei-chain.md:59` — `u` appears only on credential #3). So the discriminating fact is absent-vs-empty-vs-populated, and empty is over-loaded in the reference implementation.
- **Why it matters.** Rule 12 mandates a "persistent, non-dismissable marker that no issuer commitment attaches as presented" — the strongest, least dismissable treatment in the whole rule set. Fired on an ordinary keripy-built ACDC whose `u` was left unset, it tells a viewer a fully-issued credential is a pre-contractual sketch. That is a *new* lie, manufactured by an anti-lie rule, and it is reachable from artifacts that exist today.
- **Recommendation.** Condition Rule 12 on empty-`u` **plus** corroboration — absent Issuer commitments, which is the property the spec actually names for a metadata disclosure ("only cryptographic commitments from the Discloser are attached, not commitments from the Issuer", `spec-body.md:172`, re-confirmed) — or on host-supplied IPEX offer position. Where the corroborating signal is unavailable, the honest state is the ambiguity, per §c's own principle, not the marker. And move H6 in §e from "spec-only, no artifact" to "artifact exists, discriminator ambiguous", which is a cheaper fixture story and a more urgent one.

### F3: the host interface is seven named channels with zero providers and seven specified defaults

- **Severity:** MEDIUM  **Confidence:** LIKELY  **dedupe_key:** `host-interface-channels-without-providers`  **Objective function:** survivability  **Layer:** deployment
- **Location:** proposal §c (pairs 1, 3, 4, 5, 6, plus Rule 2b's degradation declaration and Rule 4's freshness policy); arcviz `keria-signify-surface.md`; re-anchored `src/keri/app/indirecting.py:1191, 1223, 1269` (`QueryEnd`, `/query?typ=tel`, `reger.clonePreIter`) on `upstream/main`.
- **Finding.** §c derives a host interface of seven distinct channels: attested cause metadata per unit, negotiation context, a fetch/attempt log per referenced SAID, schema resolution, event-stream updates, a per-credential freshness policy, and a degraded-outcome-space declaration. Exactly one has a decided owner (freshness policy, by Daniel's ruling, `PLAN.md` 2026-09-05 second set) and exactly one has a demonstrated provider on any surface (event-stream updates, via the witness TEL-replay endpoint — which I re-confirmed on `upstream/main`, so §B4's correction stands). The KERIA agent surface serves none of them. Meanwhile every one of the seven already has a specified honest default for absence: cause renders unknown (Rule 5), no-policy is a visible state (Rule 4), duplicity is always scoped (pair 7), a bare SAID with no schema is "hidden; protection unknown" (Rule 8). The document therefore proves, without saying so, that arcviz is fully correct with all seven channels empty.
- **Why it matters.** Each named channel is a Phase 3/4 API surface, a conformance case, and a divergence risk between the Python and React implementations held to one corpus — the carrying cost the document does not tally. Naming seven channels invites implementers to build seven, and invites a host to believe the renderer is degraded without them when it is not.
- **Recommendation.** State the normative baseline explicitly — arcviz is conformant and honest with no host annotations at all — and collapse the interface to one optional annotation channel with defined absent-semantics, of which the seven are the *vocabulary*, not seven separate contracts. Keep freshness policy called out, since it has a decision and a provider.

### F4: the closed unknown-operator question rests on keripy behavior upstream has fixed

- **Severity:** MEDIUM  **Confidence:** CONFIRMED  **dedupe_key:** `unknown-operator-rule-motivating-case-stale`  **Objective function:** survivability  **Layer:** acdc
- **Location:** proposal §f open question 5 ("keripy's coerce-and-reject behavior is the naive alternative those worked examples criticize") and §e's spec-only tier ("`DI2I` and `NOT` operators… working edge-groups"); re-anchored `src/keri/vdr/verifying.py:41, 431-440, 446-452, 454-465` on `upstream/main` `e2a1e35ca`.
- **Finding.** On upstream `main` today, `E1E` is a recognized operator in the `UnaryOps` tuple (`verifying.py:41`) with an implemented branch that enforces near-issuee equals far-issuee (`:454-465`). Tokens the verifier does not recognize are skipped and the default rule applied (`:431-440`). Only `DI2I` and `NOT` are refused, and deliberately, with a diagnosable `ValidationError` rather than an escrow — the code comment states the reasoning: "fail closed with a diagnosable error rather than being silently dropped… the chain is present and retrying cannot help" (`:442-452`). So the live case named as motivating the decision no longer exhibits the criticized behavior, and the two operators that *are* refused are refused by design, meaning a credential carrying them never reaches R0 through a keripy store and arcviz will never be handed one to render as "unevaluated."
- **Why it matters.** A decision closed against a stale motivating case will be re-opened by the first reader who checks. The rule itself survives — an arcviz built to the published spec meets `E1E` in the guardianship worked examples and must not call it invalid — but that is a *different* justification (the renderer's vocabulary lags its host's), and it should be the one written down.
- **Recommendation.** Rewrite Q5's grounds to the renderer-vocabulary case and drop the keripy criticism. In §e, record that the reference verifier now rejects `DI2I`/`NOT` outright, which changes what a keripy-fed renderer can ever be handed — and therefore whether a fixture for those cells is worth Phase 2C's budget at all.

### F5: Rule 15 bundles an unbounded export deliverable into a rendering rule

- **Severity:** LOW  **Confidence:** LIKELY  **dedupe_key:** `static-output-reverifiability-payload-unscoped`  **Objective function:** survivability  **Layer:** deployment
- **Location:** proposal §d Rule 15 ("renders every V indicator as a historical record… and carries what a re-verifier needs"), self-flagged "no audited ecosystem designed for this moment at all."
- **Finding.** Two requirements are welded together. The first half — a printed or exported view renders verification state as a historical record rather than live state — is cheap, grounded in the T axis, and falls straight out of Rule 3. The second half is an unbounded payload obligation with no stated scope: raw CESR, the anchoring KEL slice, the TEL, the schema, the far nodes? No present use case is named, no audited product implements it, and no corpus artifact exercises it.
- **Why it matters.** This is the one place in the document where surface is added for completeness of the rule set rather than against a demonstrated need, and it is the rule most likely to be silently dropped by an implementer — which then makes Rule 15 unfalsifiable as a conformance test.
- **Recommendation.** Split it. Keep the honest-degradation half as Rule 15. Move the re-verifiability payload to §f as an open question with its own demand test, phrased as "who re-verifies from a printout, and what do they have."

## Additional patterns noted

**The Phase 2C prioritization survives my scrutiny, with one carve-out.** "Target the spec-only list first" reads like the filled-for-symmetry smell, but the author's reason defeats it: the corpus-attested cells already have artifacts and the spec-only ones need construction, so that is where fixture *work* is. The carve-out is F4's: `DI2I`, `NOT` and edge-groups are not merely unobserved, they are cells the reference stack refuses to produce or traverse. Fixtures for them test arcviz against a hypothesis with no consumer. Order those last within the spec-only list, behind H5, H6 and H8, which a schema-conformant artifact can legitimately carry.

**The `a`/`A` leakage asymmetry is the best-earned cell in the matrix** and I want it on record as such, since my report is otherwise subtractive. It is a real, spec-textual distinction (`spec-body.md:1777`, re-confirmed, "does not expose any information about other yet-to-be-exposed fields, including their labels"), it has an executable worked example, and it is a distinction no audited product draws. That is present demand, observed evidence, and a differentiating render — the full bar.

**The citation base is a fork's working branch, not upstream.** Every `path:line` in the supporting research is stated against `~/code/wot/keripy` on `feat-indep-registry-bulk-issuance`, a branch of `dhh1128/keripy`. I re-checked each load-bearing cite against `upstream/main` (`e2a1e35ca`, 2.1.0-dev0) and every one holds at the same line, so nothing in this review turns on it — but the deliverable should say which tree it means, because "stock keripy" and a personal feature branch are not the same claim and the next reader will not do the check.

## Residual unknowns

I could not establish how a host that re-verifies at render time (arcviz's Python implementation over raw CESR) is meant to interact with a host that is store-fed (a KERIA-backed React view). F1's recommendation assumes those are two declared postures; the document treats the host as one thing. If they are meant to be one interface, F1's fix needs a posture field and I have not sized that.

I did not evaluate the dossier specification's Annotation Edge mechanism, named in §c pair 1 as the nearest thing to an erasure-attestation convention. If it turns out to be a usable convention rather than an analogue, §f question 1 is closer to closed than the document says, and F3's cause channel gains its first provider.
