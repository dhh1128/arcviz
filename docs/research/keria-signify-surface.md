## (a) The credential response shape

### The real type, and where it comes from

`signify-ts`'s `Credentials.get(said)` and `.list()` both return `res.json()` typed as `CredentialResult = components['schemas']['Credential']` (`~/code/wot/signify-ts/src/keri/app/credentialing.ts:35,267-312`). That type is auto-generated from KERIA's OpenAPI spec (file header: "AUTO-GENERATED: Only components and enums retained from OpenAPI schema", `~/code/wot/signify-ts/src/types/keria-api-schema.ts:1`). The generated shape, at `keria-api-schema.ts:317-343`:

```
Credential: {
    sad: ACDC_V_1 | ACDC_V_2;
    atc: string;
    iss: IssEvent;
    issatc: string;
    pre: string;
    schema: Schema;
    chains: { [key: string]: unknown }[];
    status: CredentialState;
    anchor: Anchor;
    anc: IXN_V_1 | IXN_V_2 | ICP_V_1 | ICP_V_2 | ROT_V_1 | ROT_V_2 | DIP_V_1 | DIP_V_2 | DRT_V_1 | DRT_V_2;
    ancatc: string;
}
```

`sad` is the ACDC itself — and it is not a summary or a projection. On the server, `GET /credentials/{said}` (current upstream, `credentialing.py:999-1049`, and identically the stale local copy's `/identifiers/{name}/credentials/{said}` at `~/code/wot/keria/src/keria/app/credentialing.py:519-575`) calls `agent.rgy.reger.cloneCreds([Saider(qb64=said)], db=agent.hby.db)` and JSON-serializes `creds[0]`. `cloneCreds` builds that dict as `sad=creder.sad` verbatim (`~/code/wot/keripy/src/keri/vdr/eventing.py:2427-2443`) — `creder.sad` is the parsed SAD exactly as it was stored, with no compaction or field-stripping applied by the server. So **whatever `e` (edges) and `r` (rules) look like in the stored credential — nested object, bare SAID string, or absent — is exactly what crosses the wire.** If the credential was granted/issued with a fully-disclosed edges block, the client gets the full nested object; if it was stored compact, the client gets the bare SAID string. Nothing server-side ever compacts a field that arrived expanded.

### `e`/`r` typing: a real discrepancy, but a documentation bug, not a runtime truncation

The generated `ACDC_V_1`/`ACDC_V_2` type on the checked-out signify-ts branch types `e` and `r` as bare `string` (`~/code/wot/signify-ts/src/types/keria-api-schema.ts:12-34`, both branches of the union). Current KERIA upstream's own OpenAPI dataclass source disagrees: `acdcCustomTypes = {"a": ACDCAttributes, "A": Union[str, List[Any]], "e": Dict[str, Any], "r": Dict[str, Any]}` (`WebOfTrust/keria@c2065970:src/keria/app/credentialing.py:93-98`) — i.e. current KERIA's own spec says `e`/`r` are objects. Fetching signify-ts's own `main` branch confirms the fix landed there: `e?: { [key: string]: unknown }; r?: { [key: string]: unknown }` (`WebOfTrust/signify-ts@main:src/types/keria-api-schema.ts:21-26`, fetched 2026-09-05), one commit after KERIA's fix (KERIA `c2065970` 2026-03-28; signify-ts `ff29aa8` 2026-03-31). The checked-out `feat/cesr-pq-codes` branch simply never picked up that regeneration — `credentialing.ts` itself is byte-identical to `main` (`diff` empty), only the generated schema file lags. **This is a type-generation staleness on one branch of one client library, not a KERIA behavior.** At runtime, TypeScript types are erased; `res.json()` returns whatever bytes the server sent regardless of which type file describes it. The practical consequence for arcviz is narrower than it first looks: a TS consumer built against the checked-out branch's types would see `sad.e` typed as `string` and might write code that doesn't expect an object — a real footgun for anyone trusting the type — but the object still arrives, and `JSON.parse` doesn't care what TypeScript thought the shape was.

### Does the client discard `e`, or does KERIA never send it? — resolved

The question in the brief (does veridian's `ACDCDetails` type drop `e` because KERIA never sent it, or because veridian discarded it) has a definite answer: **veridian discards it.** `CredentialService.getCredentialDetailsById()` calls the real `signifyClient.credentials().get(metadata.id)` (`~/code/me/veridian-wallet/src/core/agent/services/credentialService.ts:84-94`) — the same `Credentials.get()` traced above, so the runtime object it receives has the full `sad` (including `e`/`r` if present), `chains`, `status`, `anc`, `atc`, `iss`. The very next lines then hand-construct a new object literal for the `ACDCDetails` return value, reading only `acdc.sad.i`, `acdc.sad.a`, `acdc.schema.{title,description,version}`, and `acdc.status.{s,dt}` (`credentialService.ts:101-119`). `chains`, `sad.e`, `sad.r`, `anc`, `atc`, `iss`, and the rest of `status` are never referenced. Veridian's own `KeriaCredential` interface (`credentialService.types.ts:45-60`) is a hand-narrowed description of only the fields its mapping code reads — it is not a KERIA schema, and its narrowness is evidence of nothing beyond veridian's own view-model choice. This is application-layer discarding, not transport-layer omission — and it means arcviz, if it wants `e`/`r`/`chains`, must go to `signifyClient.credentials().get()` directly rather than through a wallet's already-narrowed adapter, if such an adapter is what a host app puts in front of it.

### A second export form exists and is richer than the JSON path

`GET /credentials/{said}` with `Accept: application/json+cesr` (`Credentials.get(said, true)` in signify-ts, `credentialing.ts:293-312`) returns a full CESR stream via `outputCred()` (`credentialing.py:1051-1099`, current upstream) that recursively walks and includes: every locally-held far-node credential in the edge chain, the *entire* KEL of the issuer, the *entire* KEL of the subject (if `i` is present in `creder.attrib`), and the *entire* TEL of the registry and of the credential itself — not just the single anchoring event that the JSON path's `anc`/`anchor` fields carry. This is a materially different (and materially larger) affordance than the default JSON response, and it is the only place in this surface where full KEL/TEL history is available in one call. It returns a raw CESR text stream (`Promise<string>`), not parsed JSON, so a consumer would need CESR parsing to use it — signify-ts ships that machinery (it's a CESR client), but no example consumer in this survey (veridian) uses this path at all.

## (b) What the `status` object actually means

`CredentialState = CredentialStateIssOrRev | CredentialStateBisOrBrv` (`keria-api-schema.ts:374-376`), fields `vn, i, s, d, ri, a (Seal), dt, et, ra` (current upstream dataclasses, `credentialing.py:135-169`). `et` is one of `iss|rev|bis|brv` — a TEL event type, not a verdict. `ra` is an empty dict for simple (no-backer) registries or `{i,s,d}` (`RaFields`) for backer-based ones.

**It is computed as a pure local TEL replay, not a verification result and not a cached value.** `Registry.vcState(vci)` (`~/code/wot/keripy/src/keri/vdr/eventing.py:1144-1192`) iterates `self.reger.tels.getAllItemIter(keys=vci...)` — every stored TEL event for that credential in the agent's own LMDB — every single call, takes the last one, and reconstructs a `vcstate` namedtuple from it. There is no result cache; the freshness ceiling is not request latency, it's how current the agent's own local TEL copy is, which is a separate ingestion question this survey did not trace further (**flagged as unresolved — see gap list**, since neither `cloneCreds` nor `vcState` reveal the polling/receipt cadence that keeps a registry's local TEL current).

`status` carries no information from axis V (§B3 of the disclosure matrix). It says nothing about schema conformance, signature validity, KEL anchoring, delegation, edge constraints, issuer bona fides, or duplicity. It says only: as of the last TEL event this agent has locally, was this credential's registry entry an issuance or a revocation (or backer variant), at what TEL sequence number, dated when, anchored to which KEL event (`anchor: {pre, sn, d}` at the `Credential` level, separately from `status`). `credentials().state(ri, said)` (`credentialing.ts:333-338`, hitting `/registries/{ri}/{vci}` — confirmed current upstream at `credentialing.py:1280-1332`, "does not need be controlled by us") returns exactly this same object alone, with no richer history — confirming there is no TEL *event-history* endpoint anywhere in this surface, only a latest-state snapshot (see (d), pair 6).

Veridian's own mapping confirms the "not a verdict" reading operationally: its local `CredentialStatus` enum (`CONFIRMED | PENDING | REVOKED`, `credentialService.types.ts:3-7`) is derived from `status.s` (the TEL sequence number as a string, `"0"` vs `"1"` in `ACDCDetails.lastStatus`, `credentialService.types.ts:39-42`) plus its own local metadata record — it is reading a TEL position, not anything the agent asserts about cryptographic soundness.

## (c) The trust split — who verifies what, where

**One sentence:** KERIA verifies once, server-side, at ingest — schema conformance, edge-chain validity against whatever far-node credentials it already holds locally, and TEL/registry presence within an expiry window — folds the outcome into a binary accept-and-store-or-escrow-and-hide gate, and signify-ts (and every consumer traced here) treats mere visibility of a credential via `GET` as the entire trust signal, performing no independent verification of its own.

**What KERIA's agent-side `Verifier` actually checks**, from `keripy`'s `Verifier.processCredential` (`~/code/wot/keripy/src/keri/vdr/verifying.py:107-244`), which is the single funnel every path uses — direct issuance to self, the current-upstream-only `POST /credentials/verify` endpoint (`credentialing.py:696-758`, submits `acdc`+`iss` into `agent.parser.ims` and returns a long-running operation), and IPEX grant admission (`agent.parser.parseOne(ims=...)` at multiple sites in `~/code/wot/keria/src/keria/app/ipexing.py`, e.g. line 187 for admit) — all feed the same parser/verifier pipeline:

- Registry presence: the credential's registry (`regk`) must already be a known Tever, and the credential's TEL issuance event must already exist (`verifying.py:125-134`) — otherwise it's escrowed as `MissingRegistryError` and a `telquery` cue is queued for background retry.
- A staleness gate on the *issuance event's own timestamp* (`verifying.py:136-141`, `CredentialExpiry`, default in the class definition at `verifying.py:31-34` — 3600s for the escrow timeouts, distinct from the `expiry` constructor default of 36000000000 at `verifying.py:49`, i.e. effectively unbounded unless the deployer overrides it): if too old, escrow and retry rather than reject outright.
- Schema conformance: `Schemer(raw=scraw).verify(creder.raw)` (`verifying.py:147-161`) against the resolved schema — escrows as `MissingSchemaError` if the schema isn't cached, raises `FailedSchemaValidationError` if it fails.
- Edge/chain constraints, **but only against far-node credentials this agent already has stored** (`verifyChain`, `verifying.py:400-490`): `self.reger.saved.get(keys=nodeSaid)` — if the far node isn't already `saved`, `verifyChain` returns `None`, the near credential is escrowed as `MissingChainError`, and a `proof` cue is queued. It resolves the effective edge operator (`I2I`/`NI2I`/default-injection per the spec's default rule), checks the far node's own TEL state isn't revoked or expired, and — new in this codebase per the inline comments — separately validates an edge's declared `s` (schema) against the far node when it differs from the far node's own schema.
- **Not checked here at all**: SAID self-consistency as a discrete, visible step (it's implicit in how `Creder`/`Serder` parse the SAD — malformed SAID would fail construction, not surface as a `Verifier` check outcome); signature validity and KEL-anchoring of the *credential's own* anchoring event (that was already checked by `Kevery`/`Tevery` when the anchoring KEL/TEL event itself was originally ingested, before `processCredential` ever runs); duplicity (a watcher-side concern, entirely separate subsystem); issuer bona fides beyond the one-hop edge-chain check; anything about a delegator's KEL reachability beyond what the near credential's edges name.

**The gate is binary and the checks are invisible once passed.** A credential that clears all of the above is written via `saveCredential` (`verifying.py:363-389`) and becomes visible at `GET /credentials/{said}` (current upstream guards on `agent.rgy.reger.saved.get(keys=(said,))`, `credentialing.py:1033-1036`). A credential that fails any check is escrowed (`mre`/`mce`/`mse`) and the `GET` 404s. There is no third state visible to the client and no way, from a *successful* `GET`, to learn which of the checks above ran or how they resolved — passing is implicit in existence. On failure, only the client-driven `/credentials/verify` path (current upstream only — absent from the stale local KERIA) surfaces anything textual: the long-running operation resolves to `{done: true, error: {code, message}}` where `message` is the raw Python exception string (`~/code/wot/keria` current, `credentialing.py:741-758` submits; `WebOfTrust/keria@main:src/keria/core/longrunning.py:234-239` for the error-wrapping), e.g. a `FailedSchemaValidationError` or `MissingChainError` message — informative prose, but a single terminal pass/fail per submission, not the four-valued per-check vector (pass/fail/unperformed/unperformable) the disclosure matrix's §B3/Rule 2 calls for, and not available at all for a credential that's already `saved`.

**signify-ts performs no independent verification of inbound credentials.** `Credentials.get()` and `.list()` are direct `res.json()` passthroughs (`credentialing.ts:267-312`); nothing in the file recomputes a SAID, checks a signature, or re-derives anything cryptographic on receipt. `Saider.saidify` appears only when the client is *constructing* a new credential to issue (`credentialing.ts:359-375`), never on the receive path. The same holds for IPEX admission in this survey's real consumer: veridian's `ipexCommunicationService.ts` uses `Saider.saidify` only to build its own outgoing admit/offer/grant messages (lines 820, 823, 936, 1095), never to check an inbound one.

**Veridian's own code confirms the trust model empirically.** After an IPEX grant, `ensureCredentialAvailable()` (`~/code/me/veridian-wallet/src/core/agent/services/credentialService.ts:322-349`) polls `signifyClient.credentials().get(credentialId)` with retries and a fixed delay, treating a 404 as "not ready yet" and any non-404 response — success — as the acceptance signal. It never inspects the credential's own content for validity; the sole criterion is whether KERIA's server-side gate has let it through yet. This is exactly what the architecture above predicts: for a browser client, "verified" *is* "KERIA hasn't 404'd it."

## (e) Edge/chain retrieval and its cost

**Within one agent's wallet, chain retrieval is free — because the agent refuses to accept anything else.** `cloneCreds` recursively embeds every edge's far-node credential in the `chains` array (`~/code/wot/keripy/src/keri/vdr/eventing.py:2416-2425`), calling itself on each `chainSaids` entry. That recursion can only succeed because `Verifier.processCredential`'s edge check (`verifying.py:400-490`, traced in (c)) requires every far node to already be `self.reger.saved` **before** the near credential is itself accepted and saved. So by induction, any credential visible via `GET /credentials/{said}` already has its entire edge chain resident locally, and the server hands the whole thing back in one response — expanding an edge that's already in the payload's `chains` array is a **local, in-memory operation** on data already downloaded, not a new network round trip.

**Getting a far credential into the wallet in the first place is not free, and is not something KERIA or signify-ts do unilaterally.** There is no "fetch this ACDC by bare SAID from the network" resolver anywhere in this surface: `Schemas.get`/`credentials().get` are local-cache lookups (404 on miss), and `Oobis.resolve` needs an OOBI *URL*, not a bare SAID. A far-node credential arrives only via an explicit disclosure act — a separate IPEX apply/offer/agree/grant/admit round trip for that specific credential, or the holder having been issued it directly and independently. This matches the corpus's own account of the real vLEI chain (each credential in the chain was independently held, not fetched on demand) and is consistent with the disclosure-matrix's framing of fetching as an intent boundary (§c pair 4, citing `papers-intent.md` affordance 4): the architecture makes that boundary structural, not just a UI convention arcviz has to enforce on top.

**When a chain is incomplete, the failure mode is a crash, not a clean H7.** `Verifier.processCredential` escrows (`escrowMCE`, queues a `proof` cue) and never saves a credential whose edge chain doesn't fully resolve — so a credential with a genuinely missing edge target simply never becomes visible via `GET` at all; the client sees a 404 for the *near* credential, indistinguishable at the HTTP layer from "this SAID doesn't exist." Separately, `CredentialResourceEnd.on_get`'s JSON path (current upstream, `credentialing.py:999-1049`) only guards the top-level `said` against `HTTPNotFound` (`reger.saved.get(keys=(said,))`); it does not additionally guard `cloneCreds`'s recursive walk of `chains`. Given the induction above, that recursive walk should never hit a genuinely missing chain SAID for anything already in `reger.saved` — but this is **inference from the accept-gate's logic**, not something exercised by a test read in this pass, and delegation (`di`/KEL, a different mechanism from ACDC edges entirely, checked by `Kevery` rather than `Verifier.verifyChain`) is exactly where the real vLEI corpus shows a hole (`corpus-vlei-chain.md` §3, cited in the matrix at H7/R1). Nothing in this survey's traced surface exposes a delegator's KEL alongside a credential response — `Credential.anc` is a single anchoring event, not a KEL — so walking a delegation chain (as opposed to an ACDC edge chain) requires a separate `KeyEvents.get(delegatorPre)` call, which itself only succeeds if this agent has separately resolved that AID.

## (f) Gap list — what arcviz needs that this stack does not provide

1. **No per-check verification vector.** Nothing in `Credential`, `CredentialState`, or any op result exposes the four-valued (pass/fail/unperformed/unperformable) outcome per check the matrix's §B3/Rule 2 requires. The entire bundle — schema, edge-chain-to-local-material, TEL presence — collapses into one binary signal: the credential is visible, or it 404s. Arcviz cannot render a verification vector this transport does not carry; a host wanting one would have to run its own `POST /credentials/verify` and parse the resulting error prose per check, which only works pre-acceptance and returns free text, not structured codes.
2. **No attested-cause metadata** for why a unit is at H2–H5/H8 (§c pair 1). Rule 5's "cause renders as unknown unless attested" will always render "unknown" against this transport, because the transport supplies no attestation channel at all.
3. **No TEL event-history endpoint**, only latest-state snapshots (`status`, `credentials().state()`). Rule 3's as-of scoping and the matrix's §c pair 6 (not-revoked vs revoked-beyond-the-horizon) have no richer data to draw on than a single `dt` on the latest event; there's no way to show reconciliation lag or a sequence of TEL events without a capability that doesn't exist here.
4. **No fetch/attempt log**, structured or otherwise (§c pair 4). A host must build and own this itself around every `credentials().get()`/`oobis().resolve()` call if arcviz's H7 rendering is to distinguish not-fetched from never-provided.
5. **No `dp` (disclosure-path) surface in signify-ts's typed IPEX API** (§c pair 3), despite the underlying grammar existing in keripy's own worked examples. A host wanting to show negotiation-state-dependent cause (compact-pending vs withheld-final) would need to read raw EXN payloads by hand.
6. **No duplicity/watcher-count surface** found in the traced client methods (§c pair 7) — though `Escrows`, `Groups`, and `Challenges` were not opened and this should be treated as incomplete coverage, not a confirmed absence.
7. **No delegator-KEL bundling with a credential response.** `anc` is one anchoring event, not a KEL; walking delegation requires a separate, independently-resolved `KeyEvents.get()` call per delegator in the chain, and nothing here confirms what happens (clean H7, or a crash) when that resolution has never happened — flagged as inference in (e), worth an integration-level check before Phase 3 designs around it.
8. **Client-side type/runtime mismatch risk**, not a missing capability but a live footgun: the exact generated TypeScript type for `sad.e`/`sad.r` depends on which signify-ts branch/regeneration a host app is built against (traced to differ between the checked-out branch and upstream `main` as of the fixes dated 2026-03-28/31). Any code arcviz ships that consumes this type directly should treat `e`/`r` as "object when expanded, string when compact" regardless of what a given vendored type file claims, and should not assume the type file is authoritative over the runtime payload.
