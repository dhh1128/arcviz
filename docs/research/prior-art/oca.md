# Prior art: Overlays Capture Architecture (OCA)

Audit stream 1B. All claims below carry a source key resolved in [`../../../refs/sources.oca.yaml`](../../../refs/sources.oca.yaml); quotes are verbatim with locators; captures live in [`../../../refs/captures/oca/`](../../../refs/captures/oca/).

## What OCA is, and its status

OCA is a data-capture and metadata architecture from the Human Colossus Foundation (HCF), built around a "Capture Base" (the raw schema) plus a set of independently-versioned "Overlays" that each attach one kind of metadata to that schema. The live specification states its own purpose: "OCA represents transient objects (domain-agnostic) and persistent schemas (domain-specific) as multi-dimensional objects consisting of a stable capture base and interoperable overlays." [oca-spec-v2, §Introduction/How does OCA work?]

The specification is actively maintained and versioned independently of any particular consumer (Aries, Swiss eID, etc.). The page metadata block reads: "Version: v2.0.0" with "Latest published version: https://oca.colossi.network/specification/" and a "Previous published version" pointing at v1.0.1, governed by a "Technology Council" at the Human Colossus Foundation. [oca-spec-v2, top-of-page metadata block] Authorship: "Paul Knowles (Human Colossus Foundation), Ryan Barrett (Stratosoft LLC), Robert Mitwicki (Human Colossus Foundation), Michal Pietrus (ArgonAUTHs), Marcin Olichwiruk (ArgonAUTHs), Philippe Page (Human Colossus Foundation)." [oca-spec-v2, top-of-page metadata block] License is "EUPL v1.2." [oca-spec-v2, top-of-page metadata block]

**The version the Aries ecosystem built against is not the version live today**, and the difference matters (see the taxonomy section below). Aries RFC 0755 links its Capture Base and overlay definitions to `https://oca.colossi.network/v1.1.0-rc.html` [aries-0755, lines 148, 210-219], an October 2022 release candidate. I captured that exact snapshot via the Wayback Machine (`2022-10-06`) rather than relying on memory of what it said. [oca-v1_1_0-rc-wayback] The overlay taxonomy has changed materially since then — see below.

## The capture-base / overlay model, and the complete overlay taxonomy (current spec, v2.0.0)

Capture Base, verbatim: "A `Capture Base` is a base object that defines a single dataset in its purest form, providing a structural base to harmonise data. The object defines attribute names and types." [oca-spec-v2, §Capture Base] It supports seven core attribute types: Text, Numeric, Reference (a SAID pointing at a nested object), Boolean, Binary, DateTime, and array-of-any-of-those. [oca-spec-v2, §Attribute type]

Overlay, verbatim: "Overlay as a task-specific object provides layers of definitional or contextual metadata." [oca-spec-v2, §Overlays] The spec deliberately keeps the base set small: "The OCA Specification intentionally limits the number of predefined base overlays to a minimum, allowing the community to take the lead in developing additional overlays as needed." [oca-spec-v2, §Overlays]

The current spec (v2.0.0, fetched live) defines exactly **13 base overlays**. I read every one and quote its defining sentence below, with my classification of presentational (governs what a human sees) versus structural (governs validation, encoding, or mapping — a prerequisite for correct display but not display itself):

| Overlay | Defining sentence (verbatim) | Presentational? |
|---|---|---|
| Character Encoding | "A Character Encoding Overlay defines the process of assigning numbers to graphical characters... allowing them to be stored, transmitted, and transformed using digital computers." [oca-spec-v2, §Character Encoding Overlay] | Structural |
| Format | "A Format Overlay defines an input and display format for data fields." Attribute-type-specific: Text→regex, Binary→IANA MIME type, DateTime→"ISO 8601, a standard for the worldwide exchange and communication of date and time-related data." [oca-spec-v2, §Format Overlay] | Presentational |
| Label | "A Label Overlay defines human readable attribute names." Multilingual (`[language-specific object]`). [oca-spec-v2, §Label Overlay] | Presentational |
| Meta | "A Meta Overlay defines any language-specific information about a schema. It is used for discovery and identification and includes elements such as the schema name and description." Multilingual; `name`/`description` plus open-ended extra fields. [oca-spec-v2, §Meta Overlay] | Presentational |
| Standard | "A Standard Overlay defines a documented agreement or technical specification published by a standards organisation used to represent, format, define, structure, tag, transmit, manipulate, use, and manage data." Worked example: `"dateOfBirth": "ISO 8601"`. [oca-spec-v2, §Standard Overlay] | Structural (informs presentation) |
| Cardinality | "A Cardinality Overlay defines the minimum and maximum number of values that an attribute can have." [oca-spec-v2, §Cardinality Overlay] | Structural |
| Conformance | "A Conformance Overlay indicates whether data entry for each attribute is mandatory or optional." [oca-spec-v2, §Conformance Overlay] | Structural |
| Entry Code | "An Entry Code Overlay defines the entry keys in a series of key-value pairs stored in a code table... The key is a unique identifier that points to its associated value." [oca-spec-v2, §Entry Code Overlay] | Structural |
| Entry | "An Entry Overlay defines the entry values in a series of key-value pairs... A value is either the identified data or a pointer to that data." Multilingual; e.g. code `"M"` → `"Male"`. [oca-spec-v2, §Entry Overlay] | Presentational |
| Unit | "A Unit Overlay defines the units of measurement adopted by convention or law." Recommends SI. [oca-spec-v2, §Unit Overlay] | Presentational |
| Attribute Mapping | "An Attribute Mapping Overlay defines attribute mappings between two distinct data models." [oca-spec-v2, §Attribute Mapping Overlay] | Structural |
| Entry Code Mapping | "An Entry Code Mapping Overlay defines the entry key mappings between two distinct code tables or datasets." [oca-spec-v2, §Entry Code Mapping Overlay] | Structural |
| Sensitive | "A Sensitive Overlay is a specialized construct used to identify and flag attributes that require protection against unauthorized or unwarranted disclosure... including but not limited to Personally Identifiable Information (PII), Quasi-Identifiable Information (QII) or proprietary information." [oca-spec-v2, §Sensitive Overlay] | Structural (privacy signal, not itself a display rule) |

Every overlay above is a flat JSON object of named, typed key-value pairs — none embeds a markup or templating language. This is confirmed structurally by the Bundle canonical-serialization rule, which fixes the field order (`v, d, capture_base, overlays`) and requires every OCA object to carry a deterministic SAID digest computed over that canonical form. [oca-spec-v2, §Bundle/Canonical form] That is: OCA bakes "this is exactly the data the issuer signed" into the object model itself, at the cost of leaving layout entirely unspecified in the current spec.

**What the base taxonomy conspicuously omits, as of today, is display layout and branding.** There is no Layout, Branding, or Framing overlay in the current 13. Multi-attribute framing (grouping fields under section headers on a rendered card) and branding (colors, logos) are left to "community overlays," which the spec treats as first-class but does not itself define: "Community overlays are task-specific objects which are integral part of OCA Bundle. Defined by the community can be used to extend functionality of OCA Bundle." [oca-spec-v2, §Community Overlays]

## What was dropped — and why it matters for the markup-vs-data question

The version Aries pinned (v1.1.0-rc, October 2022) had a broader taxonomy that the current v2.0.0 does not: an **Information Overlay** (multilingual per-attribute help text — "An Information Overlay defines attribute field descriptions and usage notes to assist the data entry process" [oca-v1_1_0-rc-wayback, §Information Overlay]), a **Credential Layout Overlay**, and a **Form Layout Overlay** ("A Credential Layout Overlay defines presentation information required by an application to display a digital credential." [oca-v1_1_0-rc-wayback, §Credential Layout Overlay]).

The Credential Layout Overlay's worked example is the load-bearing evidence for the markup-vs-data question at the *core-spec* level, and it comes out firmly on the markup side. Its `layout` field is a YAML string embedding literal CSS, including a `@import url(...)` for a Google Fonts stylesheet and `@font-face { src: url(...) }` declarations pulling font binaries from arbitrary URLs, plus dozens of `style:` properties per element. [oca-v1_1_0-rc-wayback, §Credential Layout Overlay, worked example] That is a full templating/markup surface — remote font loading, arbitrary CSS, positional layout — attached to a credential an issuer controls. **This overlay does not exist in the live v2.0.0 spec.** I cannot establish from primary sources whether it was formally deprecated, silently dropped, or is pending replacement — the current spec's changelog/rationale for the removal was not present on the pages I fetched, so that provenance is a **lead**, not a finding.

The Sensitive Overlay's definition also changed in the interim, and this is worth flagging as an example of the spec still being unsettled: the v1.1.0-rc text framed it as "attributes not necessarily flagged in the Capture Base that need protecting against unwarranted disclosure" [oca-v1_1_0-rc-wayback, §Sensitive Overlay] with a literal `TODO` where content should be — i.e. that overlay was unfinished in the version Aries built against.

## OCA for Aries: the RFCs, read from the vendored copy

Three Aries RFCs are directly relevant, all read from the local vendored copy at `~/code/me/aries-rfcs` (matching the published `decentralized-identity/aries-rfcs` content):

- **RFC 0013 "Overlays"** — retired. Status note: "Although this RFP is in the retired status, the use of overlays and the Overlays Capture Architecture (OCA) is active in Aries. This RFP is an early [draft] of the OCA specification, and its content is replaced by the Overlays Capture Architecture Specification." [aries-0013, lines 4-6]
- **RFC 0755 "Overlays Capture Architecture (OCA) For Aries"** — status DEMONSTRATED, "Implemented in the Bifold Wallet." [aries-0755, lines 4-6] This is the operative RFC: it defines how an issuer packages an OCA Bundle and delivers it during credential issuance via the `oca-bundle` credential supplement in RFC 0453 Issue Credential V2. [aries-0755, lines 57-67]
- **RFC 0756 "OCA for Aries Style Guide"** — status DEMONSTRATED, same Bifold implementation note, with two coexisting layout versions (1.0 and 1.1). [aries-0756, lines 4-9, 26]

RFC 0755's stated motivation is exactly arcviz's problem: "The core data models for verifiable credentials are more concerned about the correct cryptographic processing of the credentials than about general processing of the attribute data, and the user experience of those using credentials. An AnonCreds verifiable credential contains the bare minimum of metadata about a credential--basically, just the developer-style names for the type of credential and the attributes within it." [aries-0755, lines 86-91]

RFC 0755 lists nine overlay types it expects issuers to populate — Character Encoding, Format, Label, Information, Meta, Unit, Standard, Entry Code, Entry [aries-0755, lines 166-208] — which is the v1.1.0-rc-era list (it still includes Information Overlay, which the live spec has since dropped; this is one more confirmation of the version-drift finding above). RFC 0755 also specifies exact interoperability constraints not left to the base spec: for AnonCreds ZKP-predicate dates, `dateint` (YYYYMMDD as an integer) must carry `standard: urn:iso:std:iso:1989`, `character encoding: utf-8`, `format: YYYYMMDD` [aries-0755, lines 243-251], and Unix Time similarly. [aries-0755, lines 252-257] This is precisely arcviz's "ugly machine field → human-readable, locale-aware" problem, solved by pinning a `(datatype, standard, encoding, format)` tuple per attribute — structured, not a display template.

## Branding: markup or data? — the single most decision-relevant finding

**Branding in Aries is not part of the core OCA spec at all.** RFC 0755 introduces it explicitly as "an additional Aries-specific extension overlay, the 'branding' overlay'" [aries-0755, lines 268-272], separate from the nine core overlays. Its full field set, quoted from the worked example:

```
"type": "aries/overlays/branding/1.0"
"logo", "background_image", "background_image_slice",
"primary_background_color", "secondary_background_color",
"primary_attribute", "secondary_attribute",
"issued_date_attribute", "expiry_date_attribute"
```
[aries-0755, lines 286-301]

Every field is either a URI (to an image, optionally a data: URL), a hex color code, or the *name* of an attribute already present in the Capture Base — never a style rule, never a layout coordinate, never a script. [aries-0755, lines 314-339] This is **structured data**, not markup, and the RFC makes the refusal of pixel-level control explicit: "It is deliberate that the credential branding defined in this RFC does not attempt to achieve pixel-perfect on screen rendering of the equivalent paper credential." [aries-0755, lines 341-343] Two reasons are given: discouraging holders from screen-showing credentials as paper substitutes (oversharing/forgery risk), and the intractability of per-issuer pixel-perfect layouts across "thousands of mobile phones." [aries-0755, lines 345-358] RFC 0756 (the style guide) then fixes the *rendering* side too: three enumerated layouts (list, stacked list, single-credential) that the wallet — not the issuer — controls, with the branding fields dropped into fixed slots. [aries-0756, lines 131-135, 180-211]

This is a real, load-bearing design decision, and I found corroborating evidence that it was contested and re-affirmed even more conservatively in production. Compare the core spec's abandoned Credential Layout Overlay (a CSS/YAML templating DSL, §"What was dropped" above) against RFC 0755/0756's branding overlay (nine typed fields) against the Swiss federal government's live **swiyu** wallet, which constrains the same idea further still: "The logo or icon dimensions must not exceed 512×512 pixels" [swiyu-vc-visual-oca, line 240]; "Multi-colored logos and gradients are automatically converted to a monochrome version to foster readability and ease of use" [swiyu-vc-visual-oca, line 248]; "Can I use an SVG for the logo? Only PNG and JPEG files are currently supported. SVG or other vector formats are not accepted." [swiyu-vc-visual-oca, line 802] SVG is refused specifically because it is not just an image format, it is a markup format that can carry scripts and external references — swiyu's own FAQ frames the choice as image-format-only, no vector, no color fidelity, capped size. That is three independent points on the same trajectory — HCF's own abandoned layout DSL, Aries's narrower structured branding overlay, and swiyu's still-narrower production constraints — all moving in the same direction: **away from markup, toward small, closed, typed vocabularies.**

swiyu also settles a related design question cleanly: OCA Bundle and Credential Issuer Metadata (a separate, non-OCA source of display hints) are mutually exclusive at render time — "If an OCA Bundle is present and valid, it takes priority over the Credential Issuer Metadata. If neither is declared, a fallback visualisation takes place. There is no mix of visualisation information between OCA Bundle and Credential Issuer Metadata, either one or the other is applied." [swiyu-vc-visual-oca, line 772] That "no mixing" rule is itself a security posture: it forecloses an attack where two partially-trusted metadata sources are merged and a malicious field from one overrides a benign field from the other.

## What shipped, and what implementers reported back

**BC Gov / bcgov.** The production bundle registry is `bcgov/aries-oca-bundles`, described in its own README: "This GitHub repository is for hosting published Overlays Capture Architecture (OCA) Bundles to be used by Hyperledger Aries agents (issuers, holders and verifiers)." [bcgov-oca-bundles-readme] It runs "a lightweight governance process for ensuring those contributing to the repository are the 'authority' over the OCA Bundle they are submitting/updating, and that what they are submitting is, in fact, an OCA Bundle for a published Hyperledger AnonCreds Schema and/or Credential Definition." [bcgov-oca-bundles-readme] Publication is open beyond BC Gov itself: "anyone that follows the governance process is welcome to publish their OCA Bundles here." [bcgov-oca-bundles-readme] `credebl/credebl-aries-oca-bundles` is a parallel/forked registry from a different implementer, evidence of independent reuse beyond the originating team — this is a **lead**, not read in full.

**The Bifold wallet implementation had real integration cost.** `bcgov/bc-wallet-mobile#411` ("Add OCA Bundle handling in the Aries Bifold wallet... such that it can be exposed and used in the BC Wallet"), opened 2022-07-08 and later closed, lays out the actual verification burden an implementer takes on: bundles must be located by SchemaId or CredDefId, "OCA Bundles should be signed by Schema Publishers (SchemaID) or Issuers (CredDefID)," and the wallet must verify "Capture Base attributes match those of the AnonCreds Schema." [bc-wallet-mobile-411] The issue explicitly scoped a first cut that skips signature verification "if absent" — i.e. the security-critical step was, at least initially, optional in the reference implementation. [bc-wallet-mobile-411] This is the practical cost side of the "branding is data, not markup" safety story: the data being safe from injection does not make its *provenance* verification free — someone still has to check the signature and the schema match, and the first implementation nearly shipped without doing so.

**The Swiss federal e-ID team evaluated OCA and chose not to adopt it unmodified.** In a GitHub discussion dated October 2024, HCF's own Paul Knowles and Robert Mitwicki participated directly, which makes this an unusually well-informed piece of implementer feedback rather than an outside guess. The Swiss team's stated reason: "We created the Swiss OCA specification because we felt the need to clarify points that were not clear enough in the OCA specification..." [e-id-admin-discussion-32] Specific gaps raised in that thread: Layout Overlays were an unresolved TODO in the spec at the time; there is no mechanism in OCA to declare dependencies or processing order between overlays; and the Branding Overlay's `primary_attribute`/`secondary_attribute` fields cannot force a wallet to actually respect them — "an Issuer won't be able to force a wallet implementer to have the primary and secondary attributes displayed on one or multiple lines." [e-id-admin-discussion-32, quoting bj-ms] HCF's own Paul Knowles pushed back on a proposed attribute-aggregation (concatenation) overlay, preferring granular attributes with explicit PII flagging instead, on privacy grounds. [e-id-admin-discussion-32] Net effect: even the most sophisticated, best-supported adopter of OCA judged the base spec under-specified enough, on layout and overlay ordering specifically, to fork it rather than consume it as-is — while still keeping the Capture-Base/Overlay/SAID architecture and the “branding is fields, not markup” posture. This is evidence *for* the core architecture and *against* treating the current base-overlay list as sufficient without gap-filling.

I did not find a primary-source retrospective describing OCA as abandoned or failed anywhere in this research; what I found instead is active, ongoing, multi-implementer use (BC Gov, credebl fork, Switzerland's swiyu) accompanied by real but non-fatal friction (spec gaps, verification cost, version fragmentation between OCA 1.0/1.1 layouts noted in RFC 0756 itself [aries-0756, line 26]).

## Selective disclosure / partial data: what OCA says about a field that was not disclosed

**Nothing, directly.** I searched the full live specification text for "disclos," "redact," "partial," "undisclosed," and "selective" and found exactly one hit, inside the Sensitive Overlay: "A Sensitive Overlay is a specialized construct used to identify and flag attributes that require protection against unauthorized or unwarranted disclosure." [oca-spec-v2, §Sensitive Overlay] That is a pre-disclosure privacy *flag* — "handle this attribute carefully, it's PII" — not a post-hoc rendering rule for an attribute a holder chose not to reveal. Nothing in the Capture Base, any of the 13 base overlays, or the Aries-specific branding overlay defines how a viewer should render a *missing* value versus a *zero* value versus a *legitimately empty* value. swiyu's own gloss on Sensitive Overlay behavior is consistent with this absence and forecloses any temptation to over-read the flag: "The Sensitive Overlay does just flag attributes as sensitive with a visual indicator. No further protection or privacy mechanism is applied by the swiyu Wallet based on these information. It's up to the credential issuer to preserve user's privacy." [swiyu-vc-visual-oca, line 574]

The gap is real and specific: arcviz's hardest presentation problem — distinguishing *absent* (never in the schema), *undisclosed* (schema attribute, not shared in this presentation), *redacted* (shared as a redaction placeholder per ACDC's own compact/graduated disclosure), and *unverified* — has no counterpart anywhere in OCA's overlay taxonomy at any version I examined. OCA overlays describe an attribute that *is present in the data you're holding*. They say nothing about signaling a hole in the data. This is not a criticism of OCA on its own terms — it was built for AnonCreds/general data-capture schemas, where "the attribute is absent" mostly wasn't a state that needed a display convention — but it means arcviz cannot lift OCA's overlay taxonomy wholesale and expect it to cover this project's central hard problem (AGENTS.md's framing: "never letting *absent*, *undisclosed*, *redacted* and *unverified* be mistaken for one another, or for *fine*"). That has to be original design work.

## Verdict: is OCA's overlay model a better substrate than anything else available?

**Yes, for the specific sub-problem of "prettify one attribute value using issuer-declared, locale-aware, schema-bound metadata" — adopt the pattern, do not adopt the taxonomy wholesale. Refuse the layout/branding-as-markup instinct entirely; the ecosystem's own history argues against it.**

Argument. arcviz's stated hard requirement is turning ugly machine fields — SAIDs, AIDs, ISO-8601 timestamps — into locale-correct human text, driven by the credential's schema. OCA's Format + Standard + Character-Encoding + Unit + Label + Entry/Entry-Code overlay cluster is a solved, production-proven answer to exactly that: a `(datatype, standard, format, encoding, unit)` tuple per attribute, keyed off the schema, versioned and content-addressed independently of the schema itself via SAIDs, with the Aries `dateint`/`Unix Time` convention as a working precedent for exactly the timestamp-prettification case arcviz names. This is a better substrate than W3C's competing tradition (JSON-LD `@context` + Verifiable Credentials Rendering) for the reason RFC 0755 itself gives: "The use of JSON-LD could provide some of the required capabilities covered by OCA (such as multilingual labels), but that solution requires adding considerable overhead and far more complicated processing to achieve a minimum of the capabilities available through OCA." [aries-0755, lines 642-645] That claim is itself Aries's own rationale rather than an independent finding of mine, but it lines up with what I read directly: OCA's presentational overlays are flat key-value JSON, trivially parseable without a JSON-LD processor, and separable per attribute rather than requiring a whole-document semantic graph.

Where I refuse OCA is the base spec's now-abandoned Credential Layout Overlay and any future overlay shaped like it. A YAML string containing `@import url(...)` and `@font-face { src: url(...) }` is a live remote-code/remote-asset loading vector inside a credential an issuer fully controls and a holder's wallet must render — this is the textbook attack surface EVIDENCE.md and AGENTS.md ask this project to be paranoid about, and it is precisely what Aries's own branding overlay design (nine typed fields, "not pixel-perfect... deliberate[ly]" [aries-0755, line 341]) and swiyu's production constraints (no SVG, size-capped, monochrome-forced [swiyu-vc-visual-oca, lines 240-250, 802]) both independently converged on refusing. Three separate parties looked at "let the issuer supply layout" and backed away from it toward "let the issuer supply a short list of named values a fixed renderer consumes." arcviz should copy that convergence, not the abandoned overlay it converged away from.

Adapt, don't adopt verbatim, because of the gaps this audit surfaces: (1) OCA has no answer at all for rendering absence/redaction/non-disclosure, which is arcviz's central hard problem — original design required; (2) the base taxonomy is still moving (Information Overlay dropped, Sensitive Overlay rewritten, Layout Overlays never finished even where a HCF-participated implementer, Switzerland, asked for them) — pinning to today's 13-overlay list as a stable target is risky; (3) the signature/provenance verification burden that makes the "structured data, not markup" safety property actually hold is nontrivial and was, per bc-wallet-mobile#411, initially skippable in the reference implementation — arcviz must not assume "OCA bundle present" implies "OCA bundle verified."

## What we should steal

- The per-attribute overlay pattern itself: separate, independently-versioned, content-addressed (SAID) metadata objects keyed to schema attribute names, rather than one monolithic display config. This lets a schema evolve and a display layer evolve on different clocks, and lets multiple parties (issuer, wallet vendor, third party) publish competing or complementary overlays for the same Capture Base.
- The `(datatype, standard, format, encoding)` tuple-per-attribute as the mechanism for machine-field prettification — this is directly reusable for SAID/AID/timestamp rendering, and the Aries `dateint`/Unix-Time convention is a concrete worked example to crib from.
- Multilingual overlays as *separate objects per language* rather than one object with embedded per-locale maps — keeps a translator's diff small and reviewable, and lets a wallet fetch only the locale it needs.
- The branding-as-nine-typed-fields pattern, further hardened per swiyu's production constraints (raster only, size-capped, no arbitrary color depth) — copy the shape, tighten it further if anything.
- The explicit refusal of pixel-perfect issuer-controlled layout, and the stated reasons (anti-oversharing, anti-forgery-by-screenshot, cross-device intractability) — this is directly applicable reasoning for arcviz, not just a borrowed mechanism.
- Mandatory signature-over-canonical-form via SAID for any issuer-supplied display metadata, so a holder or verifier can prove the branding/labels came from the issuer and were not tampered with in transit — but unlike the BC Gov reference implementation, arcviz must not make this step optional.

## What we should refuse

- Any overlay, current or historical, that embeds a styling/templating/markup language as a string value (the retired Credential Layout / Form Layout Overlays). No CSS-in-JSON, no YAML-encoded layout DSL, no `style:` string properties, ever, regardless of provenance.
- Treating "OCA Bundle present" as sufficient without verifying issuer signature and Capture-Base-to-schema match — this was the exact gap flagged, and initially left optional, in the Bifold reference implementation.
- Assuming the current 13-overlay taxonomy is settled or complete — it visibly is not (Information Overlay dropped since Aries adopted it; Sensitive Overlay rewritten; Layout Overlays never finished).
- Borrowing OCA's silence on non-disclosure as license to leave arcviz's own absent/undisclosed/redacted/unverified distinction unspecified — OCA simply never had to solve this problem, so its lack of a mechanism is not evidence the problem is easy or optional.
