# Prior art: wallet paradigms (Apple, Google, ISO mDL, EUDI)

Audit stream 1C. Sources for every claim below are keyed against [`../../../refs/sources.wallets.yaml`](../../../refs/sources.wallets.yaml), which follows the record format documented at the top of [`../../../refs/sources.yaml`](../../../refs/sources.yaml). Apple and Google product UI is not reproduced here or in `refs/` — this report describes it in prose and quotes only the vendors' own developer-documentation text, which is publicly published and captured to `refs/captures/wallets/`.

The four ecosystems covered: Apple Wallet / PassKit / ID in Wallet, Google Wallet, ISO/IEC 18013-5 (mDL) and 18013-7 (online presentation) as documented by AAMVA's implementation guidelines, and the EU Digital Identity Wallet's Architecture and Reference Framework (ARF) v3.0.0.

## 1. Selective disclosure in the UI

**What the user sees about what they sent and withheld, and whether withheld data is visible as withheld or simply invisible.**

### Apple

Apple's Verify with Wallet flow is built around a *purpose string*: the requesting app must supply a sentence explaining why it needs the data, which "the system displays ... in the verification sheet so people can make an informed decision" [apple-hig-wallet, "Identity verification"]. The guidance is explicitly to under-ask: "Ask only for the data you actually need. ... if you need to ensure that a customer is at least a certain age, use a request that specifies an age threshold; avoid requesting the customer's current age or birth date" [apple-hig-wallet, "Identity verification"]. Retention is disclosed in the same sheet: "When you use PassKit APIs to specify a duration ... the system automatically displays explanatory content in the verification sheet" [apple-hig-wallet, "Identity verification"], confirmed independently by the developer portal's `PKIdentityIntentToStore` framing [apple-verify-with-wallet, "Privacy preserving": "you provide full transparency into the identity information your app requests and for how long"].

For ID Verifier (a business reading a customer's ID), the Display Only mode is a stronger form of the same idea: "the customer's data remains within the system-provided UI and isn't transmitted to your app" at all [apple-hig-id-verifier, "Best practices"] — the requester's app never receives the fields, only a match/no-match signal the user's own device renders.

What is not documented: whether the *requester's own* consent sheet shows a withheld/redacted list distinct from a granted list, versus simply a checklist the user can uncheck. The captured pages describe the request and the duration, not a positive "these fields were NOT sent" affirmation after the fact.

### Google

Google's design is closer to a two-step reveal-then-consent flow: the selector screen (rendered by the OS) shows which credentials are eligible, and a separate confirmation screen "rendered by Google Wallet" shows "the name, logo, and privacy policy that the developer provides" [google-identity-verify-overview, "Key Notes"]. For proximity/offline presentation the same principle is stated directly: "Users have the option to review requested data before sharing, and only need to share the elements relevant to the transaction rather than their entire ID" [google-identity-verify-overview, "Accept IDs in Person (Offline)"].

One concrete UI constraint the FAQ confirms and that limits relying-party control over the disclosure narrative: "Is it possible to customize the order of requested attributes on the user consent screen? A: No, Google Wallet reorders them alphabetically" [google-identity-verify-faq, "User Experience (UX)"]. Google also states apps "cannot silently query the wallet" — every request is user-invoked [google-identity-verify-overview, "Privacy-Forward & Zero-Knowledge Proofs (ZKP)"], and layers Zero-Knowledge Proofs "on top of existing ISO 18013-7 mdocs" so an attribute like age-over-18 can be proven "without revealing the actual underlying data" [google-identity-verify-overview, same section]. As with Apple, the captured docs describe the request-review step, not a distinct post-transaction "here is what stayed hidden" affirmation.

### ISO 18013-5 / mDL (via AAMVA)

This is the most explicit of the four on withheld-vs-disclosed, because AAMVA's guidelines impose UI requirements the base ISO standard deliberately does not. Two rules stand out. First, summarized requests must stay auditable: "If the request is presented in summarized form in the user interface (e.g. 'Identity and driving privilege data' as opposed to 'First Name, Last Name, DOB, Driving privileges'), means must be available to give the mDL holder visibility of the details of such a summarized form, both before and during a transaction" [aamva-mdl-implementation-guidelines-v1.6, section 4.2]. Second, "blanket sharing" (a saved profile that auto-releases a set of fields) must not make disclosure invisible: "If blanket sharing options are used, measures must be implemented to ensure that the mDL holder remains aware of what is being released when such an option is in effect" [same, section 4.2]. AAMVA further requires that the holder can always inspect the full underlying document, not just what was requested: "An mDL holder must be able to view all functional data elements if the mDL holder so chooses" [same, section 4.11]. Crucially, however, **none of this is in the ISO standard itself** — "ISO/IEC 18013-5 ... on purpose does not address the user interface (e.g. the look, feel and functionality of an mDL app residing on an mDL holder's device). It is left up to Issuing Authorities (and their implementers) to innovate in this area" [aamva-mdl-implementation-guidelines-v1.6, section 2]. So the disclosure-transparency behavior described here is AAMVA policy layered on top of a UI-silent protocol, not a standard requirement every mDL implementer must meet.

### EUDI

The ARF's design guide is the most prescriptive about *withheld-as-visible* of the four sources: "The EUDI Wallet should provide clear options for selective disclosure, allowing users to choose between mandatory and optional information to be presented... It is recommended that optional data shall be grouped in collapsed sections and be unselected by default. On the other hand, it should be clearly depicted that mandatory data cannot be unselected. The app should show users a concise summary of the requested data, clearly indicating which fields are mandatory and which are optional" [arf-annex-5.02-design-guide-data-sharing, section 3]. That is an unselected-by-default, collapsed-but-visible model — withholding is a state the optional-field checkbox is already in, not an invisible absence.

The ARF also names an orthogonal failure mode neither Apple nor Google's docs address: what a relying party sees when the *user* declines. "When the presentation of an attestation is denied by the User, the Wallet Unit SHALL behave towards the Relying Party as if the attestation did not exist" [arf-topic-d-embedded-disclosure-policies, REQUIREMENT 4] — denial must be indistinguishable from non-possession, specifically to prevent the relying party from learning that a withheld credential exists at all. This is disclosure-hiding aimed outward (at the relying party), which is a different axis from disclosure-visibility aimed inward (at the user), and the two should not be conflated when arcviz designs its own affordance.

## 2. Verification state

**How "this is verified" is signalled, and whether anything distinguishes cryptographic validity from issuer trust.**

### Apple

Apple's model layers three separate facts under one word, "verified." (1) Signature validity: "IDs in Apple Wallet use an issuer-provided signature to allow any ISO/IEC 18013-5 compliant reader to verify a user's ID" [apple-security-of-ids, "Identity data integrity and antiforgery"]. (2) Issuer trust, asserted as already resolved by the time the app sees data: "Identity information that your app gets via Verify with Wallet has been verified by the government issuing authority" [apple-verify-with-wallet, "Verified and authenticated identity data"]. (3) Reader trust, shown to the *holder* as a distinct signal: "if the reader has its own certificate that's trusted by Apple Wallet, an icon is shown to them to give the user an assurance that they're interacting with the intended party" [apple-security-of-ids, "Informed consent"]. Apple does distinguish cryptographic validity from a business's claimed identity — reader authentication requires registering with Apple Business Register to get a name/logo shown at all [apple-hig-id-verifier, "Best practices"] — but the developer docs captured here do not describe a UI state where signature-valid-but-issuer-untrusted is shown differently from fully verified; Apple's stance is that unless both hold, the credential simply isn't presented.

### Google

Google's language is similar — "Trusted, Verifiable Signals: Move beyond self-declared information. Receive cryptographically signed identity and age attributes from government-issued or trusted private issuers" [google-identity-verify-overview, "Why Integrate with Google Wallet?"] — collapsing cryptographic validity and issuer trust into one marketing claim. On the verifier side, trust in the counterparty is handled via PKI hierarchy rather than a single "trust mark": Verifier Registrars operate as Certificate Authorities issuing leaf certificates to end relying parties, and "Google allowlists the Verifier Registrar's Root CA certificate" [google-identity-verify-faq, "Verifier Registrars"] — this is closer to the ISO/mDL VICAL model than to a badge-based signal.

### ISO 18013-5 / mDL (via AAMVA)

This is the one ecosystem whose primary open documentation states cryptographic-vs-issuer-trust as two named, separate conditions: "An mDL verifier generally trusts mDL information if both the following conditions are met: 1. The mDL verifier can verify that the mDL was issued by a bona fide Issuing Authority. 2. The mDL verifier can confirm that the mDL information has not been changed since it was created by the Issuing Authority" [aamva-mdl-implementation-guidelines-v1.6, section 5.1]. Condition 2 is pure signature verification; condition 1 is a policy decision routed through the Verified Issuer Certificate Authority List (VICAL) — AAMVA's own Digital Trust Service (DTS) "confirms the bona fides of an Issuing Authority prior to inclusion in the VICAL" and "ensures the integrity of the VICAL... including the removal of public keys when the associated solutions become non-compliant with requirements" [aamva-mdl-implementation-guidelines-v1.6, section 5.2]. This is the clearest primary-source articulation among the four of "cryptographically valid" and "issuer is trustworthy" as genuinely separable facts, though it describes the *verifier's* trust decision, not necessarily anything the mDL holder sees on their own screen.

### EUDI

EUDI separates two different "verified" claims into two different mechanisms. Wallet-solution trust (is this app a genuine, certified EUDI Wallet) is the Trust Mark, deliberately UI-surfaced and click-through: it "renders the official Trust Mark graphics and/or logo, shows an informational text about Wallet Solution certification... and provides web links to a list of certified Wallet Solutions" [arf-main-06-trust-model, section 6.5.3.7]. Relying-party trust (is this requester legitimate) is a separate badge described in the design guide: "The EUDI Wallet should incorporate clear information and visual indicators or badges e.g. Trust Mark could be utilised to indicate whether the Relying Party is considered trusted... Further information must be provided upon clicking on the badge regarding what it means to be a trusted party and how you become one" [arf-annex-5.02-design-guide-data-sharing, section 3, "Relying Party Trustworthiness"]. Attestation cryptographic validity, meanwhile, is handled through the LoTE/Trusted-List chain described in the trust-model chapter and is not itself claimed to be shown to the user as a distinct icon in the captured text. So EUDI names three trust objects (wallet solution, relying party, attestation signature) where Apple and Google's captured docs name effectively one ("verified").

## 3. Many cards

**How a wallet of many credentials is navigated, stacked, or filtered.**

### Apple

Apple documents the collapsed/stacked-card interaction directly: header fields are "the only field that is visible when the passes are stacked up in Wallet, so use them sparingly" [apple-hig-wallet, "Pass field types"]. On Apple Watch, "Wallet displays passes in a scrolling carousel of cards. ... People can tap a pass on their Apple Watch to reveal a details screen that displays additional information in a scroll view" [apple-hig-wallet, "watchOS"]. This is a single flat list/stack model — no folders, tags, or credential-relationship-based grouping described.

### Google

No design guidance on multi-pass navigation was found in the captured Generic Pass overview or brand guidelines; those pages describe individual pass anatomy, not the wallet-level list. `multipleDevicesAndHoldersAllowedStatus` on `GenericClass` [google-genericclass-reference] governs whether one class of pass can be saved by multiple holders/devices, which is a provisioning-scope control, not a navigation affordance — worth flagging as a distinct concept from "many cards in one person's wallet."

### ISO 18013-5 / mDL (via AAMVA)

AAMVA addresses the *multiple-mDL-per-device* case explicitly as a scenario the Issuing Authority must decide to support or not, but stops short of prescribing UI: "mDL holders share the same device. In this case, multiple mDLs are installed on the same device, with the single device used by multiple persons... Issuing Authorities should identify the combinations that may apply in its jurisdiction and make a conscious decision on which combinations it will support" [aamva-mdl-implementation-guidelines-v1.6, section 6.3, preceding "Operational considerations"]. As with question 1, this sits inside AAMVA's added UI-adjacent guidance rather than the ISO standard, which is UI-silent by design [aamva-mdl-implementation-guidelines-v1.6, section 2].

### EUDI

The ARF design guide names "Browsing credentials/documents" as a section heading with the note "Guidelines in relation to displaying a list of credentials/attestations in the EUDI Wallet" [arf-annex-5.01-design-guide, section 3.2] — and then does not elaborate it. This is itself a finding: as of ARF v3.0.0 (July 2026 pin), the EU's own design guide flags many-cards navigation as an area needing future work rather than one it has answered.

## 4. Relationships between credentials

**Does anything represent a credential referring to or depending on another?**

### Apple, Google — no

Nothing in the captured Apple or Google developer documentation describes a credential referencing, depending on, or being derived from another credential. Apple's pass model treats each pass as an independent JSON document; nothing in the field-type or barcode documentation carries a pointer to another pass. Google's `GenericClass`/`GenericObject` split separates template from instance data but again names no cross-credential reference field. Both ecosystems' identity APIs (`Verify with Wallet`, `Digital Credentials API`) request attributes from a single credential type per call, though Google's FAQ confirms a query can name multiple credential types in one request — "Both credential types should be requested within a single `dcql` query object in the same JSON request" [google-identity-verify-faq, "Technical Integration & API"] — which is presentation-time bundling of independently-issued credentials, not a stored relationship between them. This is a confirmed no for both, consistent with the expectation that the chaining problem is unsolved in shipped consumer wallets.

### ISO 18013-5 / mDL — no, by design

The AAMVA guide's multiple-mDL discussion (question 3) is about several *unrelated* mDLs coexisting on shared hardware, not about one credential referencing another. No mechanism for inter-credential reference appears in the captured text.

### EUDI — partial yes, but explicitly unsolved

EUDI is the one ecosystem with a named concept in this territory: *combined presentation*, where a relying party requests attributes from several attestations (PID plus one or more (Q)EAAs) "in a single request and receives those attributes consolidated in a single response," with the goal of letting the relying party "verify that all received attributes belong to the same User" [arf-topic-k-combined-presentation, section 1]. The discussion paper lists candidate binding mechanisms — Relying-Party-Specific Identifiers, session-based binding, attribute-based binding (shared PID number or redundant name/DOB), issuer-attested binding, and cryptographic binding of device-bound keys — and is explicit that this is not solved: prior high-level requirements (ACP_03–ACP_09) requiring a proof of common-key-custody were withdrawn "by the fact that they rely on cryptographic mechanisms that are currently unavailable or not sufficiently mature for practical deployment" [arf-topic-k-combined-presentation, section 4.2], and the replacement mechanism is explicitly disclaimed: "This mechanism does not, by itself, guarantee that two attestations belong to the same User" [arf-topic-k-combined-presentation, section 3.4]. So EUDI is the one ecosystem naming the problem, but as of this ARF discussion-topic draft (v1.4, 19 Jun 2025, folded into v3.0.0) it has not shipped a working mechanism — this is presentation-time attribute co-verification across separately-issued attestations, not the ACDC chaining relationship (one credential's schema referencing another as an edge, independent of any particular presentation) arcviz needs to represent. Treat the overall finding as: **no shipped or standardized wallet paradigm represents a durable credential-to-credential relationship** — EUDI is trying to solve a narrower, presentation-time version of "these came from the same person," which is adjacent to but not the same problem as ACDC chaining.

## 5. Print and static rendering

**What happens when a credential leaves the screen — screenshots, PDFs, paper.**

None of the four primary-source sets captured for this stream discuss screenshot, print, or paper-equivalent rendering, with one partial exception. Apple's ID Verifier Display Only mode is explicitly designed to defeat screen capture rather than support it: it "is also designed to prevent all screenshot and screen-recording features from capturing the displayed information" [apple-security-of-ids, "ID verifier security"] — the opposite of a static-rendering affordance; it is an anti-static-rendering control. Google's captured docs are silent on the question. AAMVA's guidelines never mention "screenshot," "print," or "paper" (confirmed by direct text search of the full captured PDF). The ISO device-retrieval model is inherently a live, session-bound protocol exchange (BLE/NFC handshake, ephemeral keys, per-session MSO selection) with no standardized offline/static artifact defined anywhere in the captured material. EUDI's design guide error-states (document expired/revoked, relying party untrusted) describe live-transaction failure UI, not what a saved/printed/screenshotted credential should look like or how a verifier should treat one.

**This is a confirmed gap, not an oversight in this research pass**: none of the four ecosystems' primary documentation, as captured here, defines what a credential looks like or means once it has left the live, cryptographically-verified channel. That silence is itself evidence for arcviz's threat model — every one of these paradigms assumes the verification channel *is* the rendering channel, and none of them has a designed answer for the moment those two separate.

## What we should steal

- **Apple's purpose string + intent-to-store disclosure, both surfaced in the same consent moment.** Making "why" and "for how long" system-rendered rather than relying-party-styled text (so the relying party cannot omit or bury them) is a genuinely strong pattern [apple-hig-wallet, "Identity verification"].
- **EUDI's collapsed-and-unselected-by-default optional-field grouping**, which keeps withheld data visible as a still-present, still-inspectable, deliberately-unchecked option rather than removing it from view entirely [arf-annex-5.02-design-guide-data-sharing, section 3].
- **AAMVA's "no invisible blanket sharing" rule** — any pre-authorized/automatic disclosure path must still make the holder aware of what was released [aamva-mdl-implementation-guidelines-v1.6, section 4.2]. Directly applicable to any arcviz affordance for saved presentation profiles.
- **AAMVA/ISO's two-condition trust model (signature validity vs. bona fide issuer, verified through separate mechanisms — MSO signature check vs. VICAL membership)** [aamva-mdl-implementation-guidelines-v1.6, section 5.1] is the cleanest primary-source precedent for exactly the "cryptographically valid" vs. "I trust this issuer" distinction arcviz's threat model requires; worth modeling arcviz's own verification-state affordance on this split rather than inventing one from scratch.
- **EUDI's denial-invisibility requirement, read as a design constraint rather than copied as a UI pattern.** Hiding a declined presentation from the relying party is correct scoped to *that* audience (the RP shouldn't learn a credential exists), but arcviz's own user-facing view must do the opposite — a user reviewing their own wallet needs to see *their own* declined/withheld state clearly, so this is "steal the RP-facing hiding, keep the holder-facing visibility" [arf-topic-d-embedded-disclosure-policies, REQUIREMENT 4].

## What we should refuse

- **Collapsing "cryptographically valid" and "issuer is trustworthy" into one word or one icon**, which is what Apple's and Google's marketing-register developer docs do ("verified by the government issuing authority" [apple-verify-with-wallet]; "cryptographically signed identity ... from ... trusted ... issuers" [google-identity-verify-overview]). arcviz's whole premise is that these are different claims; none of the shipped consumer wallets' public documentation models them as visibly different states to the end user, even where the underlying protocol (ISO 18013-5's VICAL) does separate them for verifiers.
- **Treating "many cards" as a solved problem worth copying wholesale.** Apple's stacked-carousel-with-header-field model and EUDI's admittedly-unfinished design-guide placeholder are both thin; neither offers a filtering, grouping, or relationship-aware browsing model. Don't import either as if it were a mature pattern — both are, at best, a starting point for "flat list, tap to expand."
- **The assumption, implicit in all four ecosystems' captured documentation, that the live channel is the only channel.** Building arcviz around "credentials are only ever viewed through a fresh cryptographic verification" would import a gap these four paradigms all share rather than solve, given none of them designed for the screenshot/PDF/paper case (see question 5). arcviz should treat "this credential is now a static image with no live verification behind it" as a state to design for, not an edge case to ignore the way these ecosystems currently do.
- **EUDI's "combined presentation" cryptographic-binding mechanism as a model for ACDC chaining.** It solves a different, narrower problem (same-person co-verification of independently-issued attestations at presentation time) and is explicitly unfinished/immature by the ARF's own admission [arf-topic-k-combined-presentation, section 4.2]. Don't reach for it as prior art for the schema-level chaining relationship (one credential's `edges` block referencing another credential by SAID, independent of any single presentation) that ACDC actually needs represented.

## Unverified

- **Full text of ISO/IEC 18013-5:2021 and ISO/IEC 18013-7.** Both are paywalled; ISO.org blocked automated retrieval (403, Cloudflare challenge) during this research pass. Every claim in this report attributed to "ISO/IEC 18013-5" is sourced from AAMVA's implementation guidelines quoting or describing specific clauses, or from Apple/Google developer documentation describing their own conformance — never from the standard's text directly. See `iso-18013-5-lead` and `iso-18013-7-lead` in `refs/sources.wallets.yaml`, both marked `status: lead`.
- **Whether Apple's or Google's actual rendered consent-sheet UI includes an explicit "these fields were withheld" list post-transaction**, as opposed to only a pre-transaction request-review screen. The developer documentation describes the request/consent moment in detail but was not observed (by this text-only research pass, consistent with the publication-hygiene rule against capturing product UI) to describe any post-transaction disclosure summary. This should be treated as an open question, not a confirmed absence — resolving it would require either reading Apple/Google's own screenshots (restricted to `.ignored/private-refs/` per the hygiene rule) or hands-on testing of the live apps, neither of which this research pass performed.
- **EUDI ARF discussion-topic documents (K, D) are drafts, not adopted ARF requirements.** Topic K is dated "Version 1.4, updated 19 Jun 2025" and is explicitly a Discussion Paper for the European Digital Identity Cooperation Group, meaning its content is proposed language for future ARF versions, not necessarily binding on the shipped ARF v3.0.0 this report otherwise cites. Treat its content as directional, not as an adopted requirement, unless independently confirmed against a later ARF main-document version.
- **Google's Wallet-app-level "many cards" navigation UI** was not found in any captured developer documentation; this report can state only that no design guidance on the topic was located, not that none exists (it may live in non-developer-facing Google product design resources this research pass did not have access to).
