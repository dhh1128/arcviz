# Prior art: W3C / W3C Credentials Community Group — credential rendering

Audit stream 1A. Scope: what the W3C Verifiable Credentials Working Group (VCWG) and its predecessor, the W3C Credentials Community Group (CCG), have produced for rendering/visualizing Verifiable Credentials (VCs). All claims below carry a source key from [`refs/sources.w3c.yaml`](../../../refs/sources.w3c.yaml) and a verbatim quote. Captures live under [`refs/captures/w3c/`](../../../refs/captures/w3c/).

## What exists

The lead's premise is half right and half stale. A W3C document that defines `renderMethod` and an SVG-based rendering type does exist, but as of this capture (2026-09-04) it is **not** a CCG report — it has graduated to the W3C Recommendation track, and its SVG-template mechanism has been **removed**, replaced by a different design.

**Verifiable Credential Rendering Methods v1.0** — `https://www.w3.org/TR/vc-render-method/`, this version `https://www.w3.org/TR/2026/WD-vc-render-method-20260822/` [vcrm-tr]. Status, quoted from the document's own "Status of This Document" section: *"This document was published by the Verifiable Credentials Working Group as a Working Draft using the Recommendation track."* [vcrm-tr-status] It also states: *"This is an experimental specification and is undergoing regular revisions. It is not fit for production deployment."* [vcrm-tr-status] Publication date 22 August 2026 (`generatedSubtitle: "W3C Working Draft 22 August 2026"`, `publishDate: "2026-08-22"` in the document's embedded ReSpec config) [vcrm-tr-meta]. Editors: Dmitri Zagidulin (MIT Digital Credentials Consortium), Manu Sporny (Digital Bazaar), Patrick St. Louis (Open Security and Identity), Isaac KOH (Infocomm Media Development Authority of Singapore); Authors additionally include Calvin Cheng and Kyle Huang Junyuan (GovTech Singapore) [vcrm-tr-meta].

The repository `w3c/vc-render-method` was created 2023-04-28 [vcrm-github-repo]. A `w3c-ccg/vc-render-method` repository also exists but is archived, and its README says only: *"This repository has moved, the new location is here: https://github.com/w3c/vc-render-method/"* [vcrm-ccg-repo-readme]. So the lead's "CCG spec" framing describes the incubation venue accurately (see History below) but not the document's current standing — this is now a VCWG Working Draft undergoing First Public Working Draft patent exclusion (FPWD published 2025-10-30) [vcrm-cfe-mail], not a CCG-only report.

The work is organized under a named task force. The W3C group page states: *"Task Force of Verifiable Credentials Working Group"*, shortname `vc-rem`, facilitator Dmitri Zagidulin, staff contact Ivan Herman [vcrm-taskforce-page].

## The rendering mechanism, in detail

`renderMethod` itself is defined in **VC Data Model v2.1** (referenced normatively by vcrm-tr) and, identically, in **VC Data Model 2.0** — verified against both the published TR and the vendored copy at `~/code/me/vc-data-model`. VCDM 2.0's reserved-extension-points table: *"A property used for specifying one or more methods to render a credential into a visual, auditory, haptic, or other format. The associated vocabulary URL MUST be `https://www.w3.org/2018/credentials#renderMethod`."* [vcdm2-rendermethod] `renderMethod` is explicitly a reserved/experimental extension point, not a core, fully-specified property: *"Implementers MAY use these properties, but SHOULD expect them and/or their meanings to change... Implementers SHOULD NOT use these properties without a publicly disclosed specification describing their implementation."* [vcdm2-rendermethod]

The rendering spec (vcrm-tr) defines one concrete `renderMethod` type, `TemplateRenderMethod`, with three "render suites" selected by a `renderSuite` string:

1. **`card`** — declarative, code-free. *"The card render suite uses JSON templates to transform a verifiable credential into a standardized data display format... Wallets that implement this method can render the standardized JSON output in their own card UI designs."* [vcrm-tr-card] The template is JSON; string values are either literals or JSON Pointer (RFC 6901) references into the credential; the processing algorithm is pure substitution with no code execution: *"Validate the template JSON object against the JSON template schema... For each string value in the template object: [substitute JSON-pointer references]... Validate the resulting JSON object against the card output schema."* [vcrm-tr-card-algo]

2. **`html`** — data-driven, executes issuer-supplied code in a mandated confined environment. *"JavaScript within the HTML fragment is responsible for rendering the filtered verifiable credential data provided via an HTML data block... hosted in a sandboxed iframe alongside the HTML template."* [vcrm-tr-html] This is the suite the security question below is about, and it is discussed in full in the next section.

3. **`nfc`** — a static binary payload transmitted over NFC, no rendering logic at all: *"The nfc render suite transmits a binary payload representing the verifiable credential over a wireless NFC connection."* [vcrm-tr-nfc]

There is **no SVG render suite in the current document.** It existed as `svg-mustache` as recently as the April 2025 editor's draft I captured (`vc-render-method-2025-04-06-ED.html`, corresponding to commit `9758ff76`) and was removed by PR #49, merged 2026-07-28 (see History). The April 2025 draft's mechanism, for the record: a Mustache-style `{{jsonPointer}}` substitution directly into SVG source text — *"Generate a map, `replacementMap`, by finding all strings in `svgImage` that start with `{{`... For each string, `templateKey`... evaluat[e]... using the JSON Pointer [RFC6901] algorithm... For every key in `replacementMap`, replace each corresponding string in `svgImage` with the associated value."* [vcrm-old-ed-algo] That old draft's entire security-considerations section was four unconverted bullet points flagged `class="issue"`: *"The list of security considerations listed below need to be converted into sections"* [vcrm-old-ed-security] — i.e., it was never finished as prose, and it said nothing about `<script>` injection inside the SVG file itself (only about missing-hash tampering and DoS via slow resource fetches).

An `OverlayRenderMethod` with an `oca-bundle-v2` render suite — linking to an external **OCA (Overlay Capture Architecture) bundle** rather than an inline template — is proposed in an **open, unmerged** PR #30 as of capture: *"Adds OverlayRenderMethod as a sibling to TemplateRenderMethod for linking a verifiable credential to an external overlay package (OCA Bundle) without prescribing a single visual template."* [vcrm-pr30-oca] This is directly relevant to arcviz's KERI/ACDC context since OCA is used in the Trust-over-IP/Hyperledger ecosystem adjacent to ACDC, but it is unmerged and unstandardized — a lead, not an accepted mechanism.

## The security posture, quoted

This is the part that matters most for arcviz. The spec does **not** stay silent — it has a dedicated non-normative Appendix A, "Threat Model" (the real "Security Considerations" and "Privacy Considerations" sections are now stub redirects: *"W3C is migrating to a holistic threat modelling approach... Please refer to Appendix A. Threat Model."* [vcrm-tr-secstub]), plus a full companion document, the "Verifiable Credentials Render Method Threat Model" [vcrm-threat-model-doc], with five STRIDE-classified threats (T1–T5) each carrying explicit Response entries.

**T2, Unsafe Rendering of Untrusted Data**, is the issuer-template-executes-in-verifier's-viewer threat named in our task. Full description: *"The Render process combines a render template retrieved via Retrieve Render Template with claim values taken from a verifiable credential, and produces output a person perceives... Both the template code and the credential values placed in the data block are untrusted input from the point of view of the software running the Render process. Template code, or a credential value it consumes, can attempt to reach the surrounding holder system or verifier system, navigate away, or load and contact external locations, giving hostile content access to the context in which it renders. Successful verification of the credential's securing mechanism confirms that the content is authentic, not that it is safe to render."* [vcrm-t2] Its mitigation, R1 "Confine the Render Process": *"The environment allows the template's JavaScript to render the credential while preventing it from navigating away, reaching the surrounding host page, and loading or contacting external content... A browser based implementation, for example, can realize it by hosting the template in a sandboxed iframe that permits scripting but blocks navigation and top-level access, together with wrapper code that adds a Content Security Policy denying network requests."* [vcrm-t2]

The normative mechanism for that outcome, from the body of the spec: *"At minimum, the environment MUST prevent navigation, loading of external content, and access to the host page in order to prevent tracking and other privacy harms... The Content Security Policy (CSP) restrictions MUST include `frame-src 'none'`. This forces the use of `srcdoc` instead of `src` for iframes, which prevents the browser from loading the HTML template... `sandbox="allow-scripts"` MUST be set on the iframe hosting the HTML template to prevent navigation and top-level access."* [vcrm-tr-hostpage] The wrapper code additionally MUST add `default-src data: 'unsafe-inline'` as the CSP for the injected `srcdoc` document, specifically *"to prevent any network requests from being made by the template code"* [vcrm-tr-wrapper]. Template integrity is bound with `digestMultibase` (SHA-256 multihash), and remote templates SHOULD be fetched via Oblivious HTTP or an equivalent relay: *"a host page SHOULD protect the privacy of any request made (for example, dereferencing `template.id`) by using Oblivious HTTP [RFC9458] or other means of disassociating the requesting client from the requested origin."* [vcrm-tr-html]

**T3, Tracking via Template and Resource Fetches**, is the "privacy beacon" half of the question. *"In the `html` render suite, a template that is permitted to load external content could also encode credential data into the URLs of resources it fetches, such as image requests, exfiltrating rendered data to an external location."* [vcrm-t3] Mitigation R1: *"The rendering environment prevents the template from initiating its own network requests, so that a template cannot fetch per-user resources or encode credential data into outbound requests while rendering."* [vcrm-t3] — i.e. the CSP `default-src data: 'unsafe-inline'` above is the load-bearing control, not an SVG-specific fix. R2 covers the case where a remote fetch is unavoidable: aggressive client-side caching plus Oblivious HTTP relay, or embedding the resource in the credential outright.

**T5, Inherited Rendering Environment Attack Surface**, is the honest acknowledgment that the sandbox itself is a trust boundary, not a proof: *"The safety of rendering inherits the security of that underlying mechanism: a defect that lets the confinement be escaped, a policy be bypassed, or the isolation between the template and the host be broken becomes a defect in the render process, even when the render method is used exactly as specified."* [vcrm-t5] Its R2 response explicitly recommends defense in depth and steering away from `html` where possible: *"constrained suites such as `card` and `nfc`, which do not execute template code, are preferred where they meet the use case."* [vcrm-t5]

**T4, Harmful Rendering Output**, covers the "visually counterfeit the viewer's chrome" family only obliquely — its stated scope is physiological harm (flashing/strobing content, sudden loud sound), not chrome-spoofing, and it is explicitly typed `Accept` for the base case: *"The possibility that arbitrary visual or auditory output can affect a susceptible person exists for any technology that renders content and is not something the Render Method specification eliminates."* [vcrm-t4] **The spec does not name "spoofing the verifier's own security chrome" as a distinct threat anywhere in T1–T5 or in the body text I captured** — this is a gap, not a silence I am inferring; I searched the full threat model and body text for "chrome", "spoof", "impersonat", "trust indicator" and found no hits.

**VC Data Model 2.0/2.1** (not the render-method spec, but the base data model, whose text is identical between the vendored 2.0 copy and the published TR) separately and independently warns against HTML/script content in credential data generally, under Security Considerations → Code Injection: *"Despite the ability to encode information as HTML, implementers are strongly discouraged from doing so... It increases the security attack surface when using this data model, because naively processing HTML could result in the execution of a `script` tag that an attacker injected at some point during the data production process."* Its suggested mitigation: *"running the HTML rendering engine in a sandbox with no ability to access the network."* [vcdm2-code-injection]

**What the reference implementation actually does** — `digitalbazaar/vc-viewer` (`https://github.com/digitalbazaar/vc-viewer`), the Digital Bazaar demo tool linked from the spec's own PR discussion [vcrm-pr49-comments]. I cloned and read the source rather than trusting the README. `index.html` sets `<meta http-equiv="content-security-policy" content="frame-src 'none'">` at the host-page level and instantiates the template renderer as `<iframe sandbox="allow-scripts allow-modals" :srcdoc="shimCode()">` [vcviewer-index] — matching the spec's MUST-level text exactly. `viewers/html.js`'s `shimCode()` method emits `<meta http-equiv="content-security-policy" content="default-src data: 'unsafe-inline'">` around the injected credential data-block and template body [vcviewer-html-js] — again a verbatim match to the spec's wrapper-code example. For the **legacy** `SvgRenderingTemplate2024` type it still recognizes, `viewers/svg-mustache.js` performs the Mustache substitution and then renders the result as `<img :src="dataURLfromSVG()">`, i.e. `data:image/svg+xml;base64,...` fed to an `<img>` tag [vcviewer-svg-js] — this is a real, code-level mitigation (browsers do not execute `<script>` elements inside SVG loaded via `<img src>`, only inside inline/`<object>`/`<embed>`-loaded SVG), though the spec text for that legacy type never says so; the safety here is an implementation choice by this one viewer, not a documented normative requirement.

## The history, and what was rejected

This traces cleanly through primary sources: the GitHub issue/PR tracker, official VCWG meeting minutes, and the `public-credentials` mailing list.

**Origin.** The CCG incubated the idea starting 2023; repo created 2023-04-28 [vcrm-github-repo]. By May 2024 the work was organized into four parallel "work streams," per Manu Sporny on `public-credentials`: *"At present, it looks like we're going to have work streams for the following renderers: * SVG * PDF * HTML + CSS * Embedded Rendering (OpenAttestation)"* [vcrm-mail-2024may-worksteams]. All four of the concrete mechanisms from that list are gone from the current spec except HTML+CSS, which subsumed the others.

**SVG and PDF Mustache removed.** PR #49, opened by Manu Sporny 2026-03-25, title *"Remove pdf-mustache render suite and svg-mustache render suite."* Body: *"This PR deprecates the svg-mustache and pdf-mustache render suites because the html render suite handles both use cases now."* [vcrm-pr49] Discussion was not unanimous at first — official VCWG meeting minutes for 2026-05-19 record Dmitri Zagidulin objecting to dropping SVG specifically: *"I'd love to keep the SVG for the moment until I can figure out how to do the equivalent with the iframe sandbox"* [vcwg-minutes-20260519], while Benjamin Young argued removal lost nothing because *"SVG mustache and PDF mustache do exactly the same thing other than the media type"* [vcwg-minutes-20260519]. The PR was ultimately merged 2026-07-28, per Dmitri Zagidulin's own follow-up comment: *"Discussed during Jul 28, 2026 call — consensus to resolve rebase conflicts and merge this PR."* [vcrm-pr49-comments] So: the group's own rationale for killing the pure-substitution SVG mechanism was not primarily "SVG substitution is unsafe" — it was "the sandboxed HTML suite is a strict superset and we don't want to maintain two mechanisms." The security upgrade (mandatory CSP + iframe sandbox) is a side effect of consolidation, not the stated reason for the merge, though it is the effect that matters to us.

**OpenAttestation embedded/decentralized renderer dropped.** The April 2025 draft I captured defined `OpenAttestationEmbeddedRenderer`, a GovTech-Singapore-contributed mechanism where the credential names a remote "decentralized renderer" service and a template identifier, and the renderer service (not the wallet) produces the final display: *"The verifiable credential specifies a decentralized renderer at `https://demo-renderer.opencerts.io`, using the template named `GOVTECH_DEMO`."* [vcrm-old-ed-oa] I confirmed by direct text search that neither `OpenAttestation` nor `EmbeddedRenderer` appears anywhere in the current (2026-08-22) published document — it has been fully removed between the two captures I hold locally. I did not find the specific removal PR in my search window; this is a fact I verified by diffing my two captures, not a claim sourced to a specific commit message.

**A pre-standard, HTML-embedding proposal predicted the exact risk the WG later mitigated.** Issue #7, opened 2024-03-22 by a third party (not later adopted, closed 2024-04-24, never merged), proposed `WebRenderingTemplate2022` — embedding an HTML template directly and named the tradeoff explicitly: *"Security Risks: The inclusion of HTML necessitates rigorous sanitisation to prevent script injection attacks."* [vcrm-issue7] This proposal predates the eventual `html` render suite by roughly two years and correctly anticipated the core problem the WG later solved with mandatory CSP + sandboxing rather than "sanitisation" (the WG's chosen mitigation is confinement of arbitrary code, not attempting to sanitize/strip it).

**A card-like, non-executing alternative was accepted for exactly the reason you'd guess.** Issue/PR #39, opened 2025-12-18 by a third party, proposed the concept later built out as the `card` render suite: *"If a credential uses this render method, it is possible to identify which data in the credential best corresponds to summary properties that would be desirable to display on a card... Summary views could display the core data fields plus one or two of the deeper fields, and detail views could display all of the fields."* [vcrm-pr39] It was merged the same day as PR #49 (2026-07-28) — the WG replaced one lost non-executing option (svg-mustache) with a new one (`card`) on the same day it removed the old one.

**Rejected/alternative approaches, named and argued against in the spec's own "Relationship to Other Technologies" appendix** [vcrm-tr-relationship]:
- *Client-determined rendering* (no mechanism at all, e.g. mDL, bare JWT VCs): *"gives the issuer no way to convey intended presentation, so credentials render inconsistently and claims or branding can be misrepresented."*
- *Credential-type-specific display registries* (Apple/Google/Samsung Wallet passes): *"requires prior knowledge of each type, does not scale to custom credentials, and cannot express issuer-specific branding... also works against the distributed, decentralized, and permissionless patterns otherwise specified to be part of the ecosystem of DIDs and VCs."*
- *Static PDF/SVG/HTML documents* (no templating): *"such snapshots do not adapt to selective disclosure, cannot be re-rendered from the verified data, and are not bound to what was secured."*
- **SD-JWT VC's `svg_templates`**, the closest direct sibling design and the one arguably most relevant to arcviz since it's a live, competing standard: *"SD-JWT VC defines a rendering property to choose between a simple method that supports a fixed set of styling attributes, and an svg_templates method that forbids any code execution and substitutes claim values into text placeholders in an SVG. The group explored this approach and found it too limited for real-world use cases: because placeholders appear only in text nodes and no code can run, data-driven presentation tools such as conditional fields, variable-length lists, value formatting, and responsive layout cannot be expressed."* [vcrm-tr-relationship] I independently verified SD-JWT VC's own text (IETF draft-ietf-oauth-sd-jwt-vc-13, §8.1.2/§8.1.2.1 and its security considerations) rather than trusting this characterization: *"svg_templates MUST contain an array of objects containing information about the SVG templates available for the type"* with substitution via named placeholders (`{{svg_id}}`) [sdjwtvc-svgtemplates], and its security text is exactly as strong as the vc-render-method spec claims: *"When rendering the SVG template, the consuming application MUST ensure that malicious metadata providers or issuers cannot inject executable code into the SVG template... The consuming application MUST NOT execute any code in the SVG template. If code execution cannot be prevented reliably, the SVG display MUST be sandboxed. Furthermore, consuming applications MUST ensure that references to external resources (images, etc.) from within the SVG cannot be used to track users or the usage of credentials."* [sdjwtvc-security] This is a genuinely stronger, simpler, MUST-level statement than anything in the W3C html-suite text, which frames the equivalent guarantees as "required security outcomes" achieved by an unspecified mechanism rather than a flat prohibition on execution.

**Pre-VC-standard prior art, for the record.** Blockcerts, cited by a community member on issue #1, has shipped an issuer-supplied `display`/`displayHtml` property since "before VCs were VCs": *"From the beginning, the `display` property... was only a HTML string (with inline CSS and base64 encoded images)."* [vcrm-issue1-blockcerts] I independently verified the current Blockcerts `cert-schema` v3.1 `displaySchema.json`, which allows `contentMediaType: "text/html"` with no sandboxing or execution constraints stated anywhere in the schema itself [blockcerts-displayschema] — the schema is silent on the exact question this audit asks; I found no accompanying security-considerations document for Blockcerts display content in the time available, so this is recorded as a gap, not a clean bill of health.

## What we should steal

1. **The layered-suite design itself**: a code-free, JSON-Pointer-substitution suite (`card`) as the default/safe path, with an explicit, opt-in, heavily-fenced escape hatch (`html`) for issuers who need real logic — rather than one mechanism that's either too weak or too dangerous for everyone. [vcrm-tr-card] [vcrm-tr-html]
2. **The specific CSP+sandbox recipe for the escape hatch**, which is concrete and directly portable: `frame-src 'none'` on the host page (forcing `srcdoc` instead of `src`), `sandbox="allow-scripts"` (or `allow-scripts allow-modals`) on the iframe, and `default-src data: 'unsafe-inline'` on the wrapper document injected into that iframe's `srcdoc` — verified as actually implemented, not just specified, in `digitalbazaar/vc-viewer`. [vcrm-tr-hostpage] [vcviewer-index] [vcviewer-html-js]
3. **Binding template integrity with `digestMultibase`** so a remotely-hosted template can't be swapped after the credential was issued/signed — directly addresses "the issuer's rendering instructions should be exactly what was attested, not whatever's live on their server today." [vcrm-tr] (table description)
4. **The STRIDE-based, five-category threat model structure** (Target / Implementation / Deployment / External / Dependency) as a template for arcviz's own threat model document — it is genuinely well-organized and each threat carries typed responses (Eliminate/Reduce/Transfer/Accept), which is more disciplined than a prose security-considerations section. [vcrm-threat-model-doc]
5. **SD-JWT VC's flat MUST-NOT-execute-code stance** for arcviz's own default/safe rendering path — it is simpler and more auditable than "confine to required security outcomes," even though the W3C group explicitly rejected it as too limited for their general-purpose ambitions. [sdjwtvc-security] For ACDC's typical use cases (chained, selectively-disclosed structured claims, not free-form documents) the limitation the W3C group cited — no conditional fields, no variable-length lists — may matter less than it does for W3C's broader constituency, and the security simplicity may be worth more.

## What we should refuse

1. **Never execute issuer-supplied code in the default/primary rendering path.** Even the W3C group, which built the industrial-strength sandbox, keeps steering people back toward the non-executing suites: T5's own mitigation says *"constrained suites such as `card` and `nfc`, which do not execute template code, are preferred where they meet the use case."* [vcrm-t5] If the W3C's own authors hedge this hard on their sandboxed escape hatch, arcviz — with no browser, no iframe, no CSP engine to lean on — should not offer an execution path as a first-class, casually-reachable feature at all.
2. **Never treat "confined to required security outcomes" as sufficient without naming the actual mechanism.** The spec's abstraction (any environment that achieves the outcome is conforming) is right for a cross-platform standard but wrong for arcviz's own implementation decisions — we are one specific renderer, not a standard for many; we should pick and document one concrete mechanism, the way SD-JWT VC's flat prohibition does, not defer the decision to "the environment."
3. **Never let a template control chrome-adjacent visual space.** This spec has no answer at all to the "counterfeit the verifier's own trust indicators" threat named in our task — it isn't T1–T5, and I could not find the words "chrome," "spoof," or "trust indicator" anywhere in the document. That is a gap in the prior art, not a solved problem we can borrow; arcviz needs to invent its own containment for this (e.g., a template render surface that is structurally incapable of overlapping/obscuring the app's own verification-status UI, by construction — DOM layering the template can't escape — rather than by policy).
4. **Never allow un-pinned remote template fetches to become a tracking beacon**, and don't treat "just use Oblivious HTTP" as a real answer for a project our size — T3's own R2 mitigation admits OHTTP is the harder-to-deploy option and that embedding is the simpler alternative: *"An issuer that prioritizes offline use and unlinkability embeds the template and its resources in the credential, accepting the increase in credential size."* [vcrm-t3] For arcviz's first cut, default to requiring embedded (data: URL) templates with a digest, and treat remote-fetch as a deliberately harder, later-phase feature.
5. **Never reuse the "sanitisation" framing** that issue #7 used ("rigorous sanitisation to prevent script injection") — the WG's own trajectory abandoned sanitization-of-arbitrary-HTML as a strategy in favor of confinement-of-arbitrary-code, because sanitizing HTML/JS correctly is a notoriously unsolved problem in general; arcviz should follow that lesson even where it doesn't adopt the WG's specific sandbox.
