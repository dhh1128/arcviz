# What verification keripy actually performs

Phase 2D-a. Ground-truth audit of the reference implementation against the nine independent checks asserted by `disclosure-matrix.md` §B3, run against Daniel Hardman's objection that keripy may already perform much of this verification and may not make the steps separable. All line numbers are against `/home/daniel/code/wot/keripy` on branch `feat-indep-registry-bulk-issuance` (read-only; not committed to, not checked out from). No source in this document is a keripy docstring's claim about itself — every line below was read.

## (a) The nine checks in keripy

| # | Check | Performed? | Where (`path:line`) | When | Throws / records | Separable & retrievable after the fact? |
|---|---|---|---|---|---|---|
| 1 | SAID self-consistency | Yes | `src/keri/core/serdering.py:688-731` (`Serder._verify`), `:2857-2913` (`SerderACDC._verify`, adds issuer-AID well-formedness); re-run narrowly at IPEX intake in `src/keri/acdc/ipexing.py:254,272` (`nserder.verify()` + `.compare(attrs[field])`) | Object construction (`__init__`, `serdering.py:539-660`) — i.e. every time raw bytes are deserialized into a `Serder`/`SerderACDC`, by default (`verify=True`) | Throws `ValidationError` (`serdering.py:627,659,702`) | **No, not after the fact.** It is a gate at construction, not a stored result. Loading from the local DB is done with `verify=False` "to avoid unnecessary reverification" (`serdering.py:559-562`) — the DB is trusted because it already passed once, not because it is re-checked |
| 2 | Schema conformance | Yes | `src/keri/core/scheming.py:220-265` (`Schemer.verify_json`, Draft-7 `jsonschema.validate`); called from `src/keri/vdr/verifying.py:154-161` | At credential ingestion (`processCredential`), and again by the issuer's own `Credentialer.validate` before issuing (`src/keri/vdr/credentialing.py:924-947`) | Throws `FailedSchemaValidationError` (`verifying.py:160-161`) / `ConfigurationError` on the issuer side (`credentialing.py:944-945`) | **No.** Pass is implied only by the credential having been accepted into the store; no schema-conformance flag is persisted per credential |

But there is no separate "check 4 = pass" record distinct from "the event is in my KEL" — the caller must trust the local node's own ingestion history, or re-derive the receipt count itself |
| 5 | Delegation chain (`dip`/`drt` anchored in delegator's KEL) | Yes, **one tier only** | `Kever.validateDelegation`, `eventing.py:2995-3104+` (docstring at `:3006-3008`: "If delegation seal found in delegator's KEL then valid delegation... Otherwise escrow or reject") | At the delegated event's own intake, checked against whatever of the delegator's KEL the node currently holds | Throws / escrows (`MissingDelegationError`, `kering.py:670`) | **No**, same as check 4: presence of the `dip`/`drt` in the local KEL implies the immediate delegator's seal was found *at that time*; nothing distinguishes "root delegation chain fully checked" from "checked one tier, deeper KEL never seen." Root-ward recursion happens only if the delegator's own inception was *also* separately ingested and validated by this node — an accident of what the node has, not a re-derivable guarantee |
| 6 | Edge constraints (`I2I`/`NI2I`/`DI2I`, far-node SAID match, far-node schema) | Yes, but conflated with unavailability | `Verifier.verifyChain`, `src/keri/vdr/verifying.py:400-490`; far-node schema override handled separately at `verifying.py:206-227` | At near-credential ingestion, inside `processCredential` (`verifying.py:171-241`) | **Critical finding: `verifyChain` returns `None` both when the far node genuinely fails a constraint (e.g. `op == 'I2I' and issuer != farIssuee`, `verifying.py:478-479`) and when the far node simply is not in the store yet (`verifying.py:418-420,471-472,475-476`).** `processCredential` treats both identically: `raise MissingChainError` and escrow for retry (`verifying.py:187-191`) | **No — and this is the sharpest finding in this audit.** keripy's own code does not distinguish "fail" from "unperformed" for this check; both are the same exception class, the same escrow table (`reger.mce`), and the same eventual fate (see (c)) |

An LE-behind-QVI chain is verified purely because the LE credential happens to carry an `I2I` edge to the QVI credential; keripy has no code path that asks "is this issuer accredited" independent of an edge being present to ask it through |
| 8 | Revocation reconciliation (TEL replay) | Yes | `Tever.vcState`, `src/keri/vdr/eventing.py:1144-1192` — replays the local TEL log (`self.reger.tels.getAllItemIter`) and returns an `Ilks.iss`/`Ilks.rev` state | On demand — `vcState` is a query method, callable at any time, not only at ingestion | **Records, does not throw.** Returns a `vcstate` namedtuple; **`processCredential` explicitly does NOT reject a revoked credential** — `verifying.py:142-145`: "no escrow, credential has been revoked... Log this and continue instead of the previous exception so we save a revoked credential" | **Yes — the one genuinely separable, re-queryable check.** `tever.vcState(vcid)` can be called again later and reflects only the TEL events actually reconciled locally, matching the disclosure matrix's own "not revoked as of the events in hand" framing (`disclosure-matrix.md:115`) |
| 9 | Duplicity detection (watcher cross-check) | Yes, but as a wholly separate, opt-in subsystem | `Adjudicator.adjudicate`, `src/keri/app/watching.py:35-140+`; requires a configured watcher set (`self.hab.db.obvs`, `:92-95`) and previously-polled watcher key state (`self.hab.db.knas`/`.ksns`, `:104-109`) | **Never automatic.** Not called from `Verifier.processCredential`, `Kevery.processEvent`, or the IPEX handler at all — it is invoked explicitly, per-AID, by a host application that has set up watchers | **Records a cue**, not an exception: `cues.append(dict(kin="keyStateDuplicitous", ...))` (`watching.py:117,130`) or `keyStateConsistent`/`keyStateLagging` (docstring `:43-47`) | **Ephemeral, not persisted per-credential.** The cue is a one-shot signal pulled off a deque (`decking.Deck`) by whatever's consuming it; nothing stores "no duplicity detected for AID X as of T" as a queryable record. It is also scoped to an AID's key state, not to a specific credential, and only as good as the watcher set actually consulted (`disclosure-matrix.md:116`, "no duplicity detected by the witnesses/watchers consulted") |

Local-duplicity detection distinct from watcher-based check 9 also exists incidentally: a second inception event for an already-known AID with a different SAID is escrowed as `LikelyDuplicitousError` (`eventing.py:4351-4356`). This is a byproduct of a single node's own event-ingestion history, not the cross-witness protocol check 9 names — it catches only what this node happens to have seen, and is not what the disclosure matrix's "duplicity" row is about.

## (b) What a credential in keripy's store means

`reger.saved`/`reger.creds` (`src/keri/vdr/verifying.py:363-389`, `saveCredential`) is reached **only** by falling through the entire body of `processCredential` without raising. So presence in the store is a real, load-bearing guarantee for four of the nine checks, at ingestion time, as of whatever the node had on hand then:

- **Check 1 (SAID self-consistency)** — guaranteed. `SerderACDC.__init__` cannot construct a `creder` object at all from bytes whose SAID does not recompute (`serdering.py:621-628`).
- **Check 2 (schema conformance)** — guaranteed against the schema resolved at that time (`verifying.py:154-161`).
- **Check 6/7 (edge constraints / issuer bona fides)** — guaranteed **only as far as the store reached at ingestion**: every edge target had to already be a previously-`saveCredential`'d node satisfying its own operator constraint (`verifying.py:171-241`). This is transitive by construction — a stored credential's whole upstream qualifying chain was checked, one hop at a time, at the time each link was separately ingested — but nothing re-verifies that chain later, and (c) below shows the "fail" and "unperformed" outcomes for this check are not even distinguished internally.
- **Anchoring plumbing (part of check 4)** — the credential's `prefixer`/`seqner`/`saider` (the anchoring KEL or TEL event identity) are recorded via `logCred` (`verifying.py:373`, called from every escrow/save path), so the anchoring locator is retrievable, though (as check 4's row states) the anchoring *event itself* having validly entered the KEL is a fact about a different data structure (the KEL), not re-attested by the credential record.

What store presence does **not** guarantee:

- **Check 8 (revocation)** is explicitly **not** gated on: `verifying.py:142-145` saves revoked credentials on purpose. A retrievable credential can be currently revoked; the caller must separately call `tever.vcState(vcid)` to learn current status.
- **Check 9 (duplicity)** is never run as part of ingestion at all; store presence says nothing about it, positive or negative.
- **Check 5 (delegation) reach** is whatever the node happened to hold at the time, with no record of how deep the chain was actually checked (this is exactly the vLEI root-KEL hole the disclosure matrix already documents, `disclosure-matrix.md:112`).
- **Nothing about staleness (T-axis)**: all of the above are as-of the ingestion moment (or, for check 8, as-of the last `vcState` call) — keripy carries no independent "this is still current" guarantee.

So Daniel's framing — "the mere fact that a credential is in hand implies some set of checks passed" — is correct, but the set is smaller and more conditional than "much of it, perhaps all nine": it is checks 1, 2, and a transitively-constructed version of 6/7, plus the bookkeeping for 4. It excludes 8 by explicit design choice and excludes 9 entirely. And even within the included set, 6/7's guarantee is corrupted by the fail/unperformed conflation in (c).

## (c) What keripy structurally cannot do alone

- **Check 9 (duplicity)** cannot complete without an externally-configured, externally-polled watcher set (`watching.py:92-109`) — it is a network protocol, not a local computation, and keripy's own code frames it as opt-in infrastructure a host must stand up.
- **Check 7 (issuer bona fides)** cannot reach further than the deepest credential the node has actually stored and ingested; keripy has no fetch-and-verify-on-demand for a missing qualifying credential inside `verifyChain` itself — a missing far node returns `None` and escrows a cue asking for it (`verifying.py:188-189`), but the check does not complete until something else (a peer, an OOBI resolution) supplies the missing artifact.
- **Check 5 (delegation) past the first tier** is the same shape of limitation: `validateDelegation` checks against "whatever of the delegator's KEL the node currently holds" (`eventing.py:3037-3038`, "only use pre-existing information... unless eager"); reaching the root requires that every intermediate KEL was independently supplied and ingested.
- **Check 8 (revocation) "as of now"** is structurally impossible for keripy to assert unilaterally: `vcState` reconciles only the TEL events the node has actually received (`eventing.py:1154-1156`, iterating `self.reger.tels`); a fresher TEL event that has not arrived is invisible by construction, not by a bug.
- **The fail/unperformed conflation in check 6** (documented in (a)) is not an external-cooperation gap like the four above — it is a genuine internal limitation: `verifyChain`'s `None` return cannot be told apart by its caller, so `processCredential` cannot correctly label a constraint violation as a permanent fail versus a transient absence. Escrows expire silently (`_processEscrow`, `verifying.py:318-361`: on `Stale event escrow` the escrow entry is simply removed and logged at `logger.error`, `:351-357`) with no persisted distinction between "the far node arrived and the constraint was violated" and "the far node never arrived at all."

## (d) Is there a per-check result surface?

**No.** Across all nine checks, keripy exposes exactly one genuinely separable, re-queryable, per-artifact status API: `Tever.vcState(vcid)` for check 8 (revocation). Everything else is either:

- baked into object construction as verify-or-throw, with pass recorded only implicitly as "the object exists" (checks 1, 2, 3, 4, 5, 6/7), or
- an ephemeral cue pushed to a `decking.Deck` and consumed once by whatever is listening (check 9's `Adjudicator` cues, `watching.py:117-140`; also the `"saved"`/`"proof"`/`"telquery"` cues emitted throughout `verifying.py`, e.g. `:189,213,223,233,244`).

There is no API, stored record, or status object of the shape "for credential X, checks 1-9 were {pass, fail, unperformed, unperformable}" anywhere in `src/keri/`. A host application that wants to hand arcviz a genuine nine-element vector would have to **construct it itself**, by instrumenting the ingestion pipeline at the moment each check runs (since most checks don't survive past the moment they run) and separately re-querying `vcState` for check 8 and standing up its own watcher/`Adjudicator` wiring for check 9. Nothing in keripy does this bookkeeping today.

## (e) What this implies for RULE 2

RULE 2 says verification renders as a vector, never a scalar, with four distinguishable outcomes per check. That rule describes a UI contract; it does not, by itself, claim the *data* behind it already exists in a form a renderer can consume. This audit shows the data mostly does not exist in that form, which means the rule needs to survive only in a weakened, honestly-scoped shape:

- **RULE 2 survives as a rendering discipline for whatever data the host does supply** — arcviz should still refuse to collapse nine potentially-distinct facts into one badge, and should still distinguish (in its own rendering, from host-supplied input) pass/fail/unperformed/unperformable wherever the host can actually tell them apart. Nothing here argues against that discipline; the disclosure matrix's underlying argument — that these are nine different epistemic claims that a single checkmark equivocates — is not weakened by keripy's implementation gaps. If anything it's strengthened: because keripy itself doesn't track the distinctions, a UI collapsing them into "verified" would be manufacturing certainty the substrate never produced.
- **RULE 2 needs weakening on the fail/unperformed axis specifically for checks 5, 6, 7.** The rule's own text calls fail and unperformed "different states" that "must render differently" (`disclosure-matrix.md:104`). For checks 6 and 7, keripy's reference implementation cannot supply that distinction — `verifyChain`'s `None` is genuinely ambiguous at the source. A host built directly on keripy as shown cannot honestly report "fail" for these two checks at all today; it can only report "unperformed/unperformable" or "pass," with a real fail collapsing into the same bucket as absence. Rule 2's test ("find any rendering where unperformed and unperformable share a glyph") should gain a sibling test: a renderer must not claim to distinguish fail from unperformed for a check where its host's substrate cannot make that distinction, and arcviz's host interface (per (d)) needs to let a host declare "this check's outcome space is degraded to {pass, not-pass}" rather than forcing the full four-value lattice everywhere.
- **RULE 2 needs a genuinely new host-interface requirement, not present in the current disclosure matrix's §c list**: since 8 of 9 checks leave no retrievable record past the moment they ran, **the default state of most checks, for a credential merely retrieved from storage, is "unperformed" from arcviz's point of view** — not because nothing happened, but because nothing survived. A host that wants arcviz to show anything other than "unperformed" for checks 1-7 and 9 must either (i) re-run verification at render/query time and hand arcviz a freshly-computed vector, or (ii) have instrumented its own ingestion pipeline to persist a vector keripy itself does not persist. Absent either, the only honest scalar-adjacent claim arcviz can render from "this credential is in the store" is closer to Daniel's framing than to RULE 2's assumption: "the substrate's ingestion gate did not reject this," which is real evidence for checks 1, 2, and the transitive part of 6/7, and is silent — not a pass — on 3, 4, 5's depth, 8's current status, and 9.
- **RULE 2 does not need replacing.** The vector framing is still the right target and the right rejection of a scalar badge; what changes is that arcviz's host interface must treat "unperformed" as the default truth for most cells rather than an edge case, and must accept a host's inability to distinguish fail from unperformed for checks 6 and 7 as a first-class, nameable state rather than a gap to paper over.
